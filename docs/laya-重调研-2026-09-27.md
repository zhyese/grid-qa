## 0. TL;DR

**Laya 能在这个项目里起什么作用**：它是一个**毫秒级、可自托管、输出"标签+校准概率"的判别式模型**，
用来接管系统里现在由「一堆手写正则/if-else」或「花几秒调一次 LLM 只为拿一个是/否」承担的那类
**边界明确的离散决策**。它能带来的真实增量有三条：

1. **把"是否 X"类 LLM 调用换成 30ms 本地调用** —— 系统里 `self_rag.need_retrieve`、
   `judge_context_relevance/answerability`、`CRAG v2 per-doc 分级`、`debate_needs_debate` 都在用整次
   LLM 换一个二值/三标签结果，`【代码】`这些点目前要么是默认关（怕延迟），要么全量采样跑（费钱）。
2. **给规则判据补语义泛化** —— `safety.py` 注入检测是 7 条正则、知识骨干 `classify_query` 是首词命中、
   演练评分是关键词子串匹配；判别式模型天然能吃"换个说法也认得"的同义表述。
3. **输出可用概率做门控** —— 这是 LLM 给不了的东西：` p(≥阈值) → 自动放行 / 低于阈值 → 转人工 `，
   与系统现有的"unsure→人工确认"红线天然咬合。

**不能指望什么**（必须写死在方案里）：
- **不能直接零样本用在自有业务标签上**。这是官方明示的：base checkpoint 在 typed-decisions 上
  0.362/0.342，随机基线 0.318，**低于多数类基线 0.461**；0.766 的 headline 来自同一基准训练集上的微调。
  官方原话是 *"a fast base to specialise, not a zero-shot decision engine"* `【官方】`。
- **不能承担需要推理/常识的判断**（社区实测：问"掷出 3，是奇数吗"，答 9%，置信 91%）。
- **不能做超过 ~20 个选项的单层分类**（Banking77 上 0.425 vs Jev 0.870）。
- **权限与执行动作永远不能由模型给出**（社区金句：*Laya only ranks survivors. Permission never comes from the model.*）。

**建议路径（一句话）**：先用**零样本就够用的通用二分类场景**（注入/越狱检测）做**工程可行性 Stage 0**（不需要一条自有标注），
跑通后再进**领域微调单点试点**；而不是一上来就投 6-7 人天造 3.5k 合成数据 + 微调，等 Stage 1 结束才看到第一个信号。

## 1. Laya 是什么（2026-09-27 事实核查）

**定义**：非自回归（non-autoregressive）的 System 1 决策引擎。输入「一段 state（文本/邮件/工单/JSON）+ 一组类型化问题」，
**一次前向**直接给出每个问题的答案分布，**不生成任何 token**，因此结构上不存在"幻觉式胡编"，只有"分类错"。

**生态水位** `【官方】`：

| 项 | 事实 |
|---|---|
| 仓库 / 作者 | `github.com/NandhaKishorM/laya`（NandhaKishor M, Convai Innovations） |
| 创建 → 现在 | 2026-09-18 创建，**9 天**到 23,805 stars / 2,045 forks / 158 open issues |
| 最新版本 | **v0.3.20**（2026-09-24 发布，PyPI 包名 `laya`）；最新合并 PR #464 是 ONNX 语言一致性修复（09-25） |
| License | Apache-2.0（code + weights） |
| 社区热度 | HN 首帖 1,352 points / 316 comments（09-19）`【社区】` |

**三个 checkpoint** `【官方】`：

| Checkpoint | 基座 | 参数量 | 上下文 | 用途 |
|---|---|---:|---:|---|
| `laya` | ModernBERT-large | 421M | **512** | 英文 |
| `laya-multilingual` | mmBERT-base | **322M** | 1024（可设 `max_len=8192`，但**可靠到约 4k token**，之后明显波动） | 100+ 语言，**中文走这个** |
| `laya-typed-decisions` | ModernBERT-large | 421M | 1024 | 官方微调示范（发票/安全事件/客服/agent 轨迹四类工作流） |

**三种决策原语**（请求时用 schema 声明，不需要重训）：

- `choice`：从你给的 N 个选项里选一个，返回每个选项的概率（如分诊类别）
- `score`：有序等级打分（如严重度 1-5）
- `noul`：yes/no/unsure 的 P(true)（如"是否需立即人工介入"）

请求/响应形态（`【官方】`README Quickstart）：

```python
questions = {
  "action":    {"type":"choice","instructions":"该走哪类处置？","criteria":{"observe":"...","isolate":"...","ticket":"..."}},
  "urgency":   {"type":"noul",  "instructions":"是否需要立即人工介入？"},
  "severity":  {"type":"score", "instructions":"综合严重程度？","criteria":["低","较低","中","较高","高"]},
}
result = router.predict(state, questions)     # answers.action.choice / .urgency.noul / .severity.score
result["routing"]["model"]                    # 'multilingual' —— 必须校验这个字段
```

**延迟**（都需要按自己负载复测）：T4 单问题 p50 **32.8ms**、batch **7.2ms/题**；**CPU 预加载 193–464ms/题** `【官方】`；
第三方在繁忙宿主上 p95 到过 **467ms**（超出其 300ms 决策 timeout 并真实触发）`【社区】`。

## 2. 为什么本项目只能选 Laya，而不是 Jev

（Jev 是 TypeSafe AI 的闭源托管同类，Jev 先出、Laya 是开源替代，两者 wire format 兼容。）

| 维度 | Jev（闭源托管） | Laya（自托管） | 对本项目的意义 |
|---|---|---|---|
| 权重/费用 | 闭源 API，waitlist，**$0.042/1M input tokens** | Apache-2.0，自托管 $0 许可费 | 电网数据**不出内网**是硬约束 → Jev 出局 |
| **微调** | **不支持** | 支持（官方 Kaggle notebook，RLCD） | **决定性差异**：运维告警/两票是自有的文标签体系，不可微调 = 必然落在"近随机"水平 |
| 单层选项数 | 支持到 255 | 共享 ~192–256 token head budget，**默认约 20** | 我们的分类需要拆级联窄问题 |
| 上下文 | ~32K | 512 / 1024（multilingual 可靠到 ~4k） | 长票据摘要必须截断/压缩 |
| p50 延迟 | 236–276ms（托管，含网络） | 32.8ms（T4 本地） | 本地更快且不受网路抖动 |
| 校准后 ECE | 0.246 | 0.081 | Laya 更优（但需自己 refit） |
| 软分布保真度 | 0.580 | 0.471 | Jev 略优；对我们"取 argmax + 阈值门控"的用法影响有限 |

**结论**：数据不出网 + 必须适配自有标签 → **只能走 Laya 自托管 + 自有数据微调**。Jev 唯一值得留作兜底的是"超多选项"（>50 类）场景。

## 3. 硬约束清单（决定形态，不可绕）

| # | 约束 | 证据 | 对本方案的影响 |
|---|---|---|---|
| 1 | **自有业务标签必须微调** | base 0.362/0.342 vs 随机 0.318 vs 多数类 0.461；微调后 0.766 `【官方】` | 否決"直接接入即用" |
| 2 | **`score` 是三种原语里最弱的** | SST-5 仅 0.372；社区实测"优先级四档全塞 medium"，`p99 4.2s + 错误率 2.1% + 三区域受影响` 这种生产事故仍给 medium（置信 0.117）`【社区】`；multilingual 的 score 还有 position bias（issue #131）`【官方】` | **旧 spec 的 `severity: score(0-4)` 必须改**——见第 9 节 |
| 3 | **`noul` 有否定敏感** | issue #377：被否定的取消请求 4/4 判成 cancel_account；issue #156：可能跟随自身 true/false 标签而非输入 `【官方】` | 电网告警里"未复归/非计划/未收到"类否定表述天然多，**训练集必须专门造否定/反向样本** |
| 4 | **选项 token budget** | 所有选项共享 192–256 token；>20 选项精度断崖；Banking77 0.425 vs Jev 0.870 | 我们的 choice 控制在 **≤8 个窄选项**，多的走级联（先大类再小类）或 `predict_shortlist` + embedding 召回 top-k |
| 5 | **上下文短** | multilingual 默认 1024 截断；8192 也只可靠到 ~4k token | 告警/票据 state 模板必须做**字段裁剪 + 截断上限**（建议 state ≤600 字） |
| 6 | **出厂过度自信** | 出厂 ECE 0.466 → 按 (type, option count) refit temperature 后 0.081；`laya-multilingual` **出厂完全没有 fitted temperatures** `【官方】` | **必须做温度拟合**，否则置信度门控是假的 |
| 7 | **confidently wrong 是头号部署风险** | 社区 30 张工单 70% 准确率，9 个错里 **6 个置信度 ≥0.98**；中文/非拉丁用英文 checkpoint 会出现 Khmer 那种"0.000 分 / 0.952 置信" `【社区】【官方】` | ①必须校验 `routing.model == multilingual`；②门控用概率但**兜底永远指向保守路径** |
| 8 | **confidence 公式与 Jev 不同** | Laya = 1 − normalized entropy，阈值不可跨模型迁移 `【官方】` | 阈值必须在本项目数据上自拟合，别抄社区的 0.85 |
| 9 | **冷/热切换开销** | `max_loaded=1` 时切换 checkpoint 需重建：CPU 中位 **7.4s**、T4 10.3s；生产必须 `preload=True` / `LAYA_PRELOAD=1` `【社区】【官方】` | 只预加载 multilingual 一个；educational 部署要常驻，不要懒加载进主进程 |
| 10 | **common sense 不在射程** | 见第 0 节骰子例子 `【社区】` | 只放"归类/是否"，推理留给 LLM |

## 4. 本轮新增：与本项目的技术兼容性实测

这是旧版报告完全没有、却直接决定"能不能落地"的部分。

### 4.1 依赖本身没有看起来的那么硬

README 那句 *"dependencies set that floor: huggingface_hub 1.x, transformers 5.x and torch 2.14"* 容易让人误以为必须大升级。
**实测 PyPI 元数据**（`【实测】`，2026-09-27）：

```
requires_python: >=3.10
requires_dist: torch>=2.0.0, transformers>=4.48.0, safetensors>=0.4.0,
               huggingface_hub>=0.20.0, numpy>=1.20.0
extras: serve / mcp / langchain / langgraph / onnx / fast
```

→ 项目现状 `python:3.11-slim` + `torch==2.13.0+cpu` **满足最低约束**，不必升 torch。

### 4.2 但真正要小心的是它会把 transformers 拉到 5.x

在隔离 venv 里跑 `pip install --dry-run laya==0.3.20 sentence-transformers>=3.0 torch==2.13.0`（`【实测】`）：

```
Would install ... laya-0.3.20 transformers-5.17.0 sentence-transformers-6.1.0
                 torch-2.13.0 huggingface_hub-1.33.0 tokenizers-0.23.2 numpy-2.5.3 ...
```

**无版本冲突，依赖可解**——但 pip 会装 **transformers 5.17.0**，而生产现有 P1 本地 bge embedding 走的是
`sentence-transformers`（`app/services/embedding_service.py` 委托 provider 链），会**同处一个解释器**。
transformers 4→5 是主版本跳变，`【代码】`虽经 providers 层隔离，但**升级前必须在 QA 主链上跑一遍 embedding/recall 回归**
（`retrieval_eval_service.evaluate_over_golden` 现成，golden 109 条，`_RECALL_GATE=0.92`）。

> 规避墙：**走独立进程/sidecar（见第 7 节）+ `laya[onnx]`**，可以让主后端**一个依赖都不动**。

### 4.3 国内源会装到两年前的老版本（坑）

`【实测】`：

| 源 | laya 可用版本 |
|---|---|
| `https://mirrors.aliyun.com/pypi/simple/` | **最高仅 0.3.5** |
| PyPI 官方 | 0.3.20 |

项目 Dockerfile 里 `pip install -r requirements.txt -i https://mirrors.aliyun.com/pypi/simple/` `【代码】`，
照抄会装到 0.3.5。**对策**：laya 单独一行，`pip install laya==0.3.20 -i https://pypi.org/simple`（Dockerfile 已有
`HTTP_PROXY/HTTPS_PROXY` build-arg 注入先例），或预先把 wheel 落到 `backend/wheels/` 离线装。

（顺带：`download.pytorch.org/whl/cpu` 上 **torch 2.14.0+cpu 已存在**，若日后需要升级不存在阻塞。）

### 4.4 运行环境与模型落盘

`【代码】`docker-compose.yml：

```
backend:  mem_limit: 10g   cpus: 4
environment: HF_ENDPOINT: https://hf-mirror.com
            HF_HUB_OFFLINE: "1"
volumes:  C:/Users/Administrator/.cache/huggingface/hub:/root/.cache/huggingface/hub:ro
```

含义三条：
1. 模型必须**先在宿主机下载到 HF 缓存**（建议 `HF_ENDPOINT=https://hf-mirror.com` +
   `snapshot_download(repo_id="convaiinnovations/laya", allow_patterns=["laya-multilingual/*"])`，
   只下 multilingual，别把 2.5GB 全拖下来 `【社区】`）；
2. 容器是 `ro` 挂载 → **容器下载不了**，离线布局和 bge 一样处理；
3. mmBERT-base 322M CPU 推理约 1GB 级常驻（端侧移植实测 ~1GB `【社区】`），**与 4 核 / 10g 上限下的
   bge embedding + rapidocr(onnxruntime) 抢资源**——这是把模型塞进 backend 容器的最大异议（见 §7）。

## 6. 建议路径与 go/no-go 门禁

> 设计原则：**每一段都先要一个"低成本信号"再决定是否继续**；红线沿用仓库既有铁律——
> 开关默认 False、`degraded(tag, e)` 不 crash、`getattr(settings,"X_ENABLE",False)` 早返回、返回保守值。

### Stage 0 —— 工程可行性 + 零样本能力验证（**2-3 人天**，目标：证明链路跑得通）

不做任何自有数据处理，**只用 slam base checkpoint 的通用能力**：

1. 隔离 sidecar 起 `laya-serve`（见 §7），单 checkpoint（`laya-multilingual`，`LAYA_PRELOAD=1`）；
2. 取 False positive/negative 对照：**注入检测** —— 用 50 条公开越狱/指令覆盖样例 + 50 条本项目真实
   运维 query（含"接地/放电/带电"等易误杀术语），对照现有正则 `detect_injection` 的 noul 结果与概率；
   同时跑 **500 次单请求压测**，量 pos p95 延迟、常驻内存、CPU 占用峰值。
3. **Go / No-Go**：
   - G1 中文 routing 校验：`routing.model == "multilingual"` 命中率 100%（防 §3 约束 7 的 Khmer 型事故）
   - G2 pos p95 **< 500ms**、常驻内存 **< 1.5GB**（backend 只剩 10g/4cpu，超了必须走独立容器）
   - G3 在易误杀样本上（如带电/接地/放电术语）相对现有正则无重大倒退——模型只作"第二意见"叠加，不替换正则

失败 → 归档，主链路零改动（sidecar 整体删容器）。

### Stage 1 —— 单点领域微调（**5-7 人天**，沿用/修正旧 spec 的数据冷启动）

仅在 Stage 0 通过后做。选 **告警进门门禁**（`evaluate_rule_gate`，二值 + 已有 `rule_decision` 落库标签，
利润/风险比最干净），**且 schema 按下节修正**。

训练集来源三路：LLM 蒸馏合成（主力，目标 ≥3000 条，每批抽 5% 人工抽检，不一致率 >10% 返工）+
规则弱监督（≥500 条，交叉验证分歧样本进抽检池）+ 真实回流（全进验证集，不进训练集）。
**注意**： `【代码】` 实测存量人工标注极少（realtime_event 51 条、proactive_ops_run confirmed 1/rejected 1、
alert_disposal 153、tickets 12），实时跟踪成熟前的信任“synthetic-first”，但必须保留真实的 gold set 作为**外推验证**。

训练/校准：跑官方 notebook（免费 2×T4，约 30k 问题 / 4-5h）；社区另有 180k 3 epochs ≈ 55min 的参考 `【社区】`。
**LoRA 是社区方案，非官方支持**，先用官方全参跑基线。

门禁（四条全过才继续）：
- **A1** 中文 accuracy ≥ 现行规则基线 +10pp（旧线，合理）
- **A2** 留出外推集（golden 规程问答）方向一致率 ≥80%
- **A3** 温度拟合后 **ECE < 0.15**
- **A4** 本轮新增硬门禁：**否定样本子集准确率 ≥ 训练集整体 -5pp**（针对 §3 约束 3）

### Stage 2 —— 单点集成 + 在线对照（**3-4 人天** + 4 周观察）

挂 `ingest_event` 后 / Agent 派发前，`asyncio.gather` 并行不增加入库延迟；结果写幂等补列 `ai_triage_json`；
前端 OperationsCenter 加"AI 预判"徽章（含 unsure 灰态）。
沿用系统现有对照设施：`eval_matrix_service.run_matrix_async`（verdict ∈ 常开候选/维持关闭/建议回收）+
按 tenant/事件哈希 A/B + `online_eval_service` 双曲线趋势。
**红线**：预判只展示，不自动触发任何设备/工单动作；模型不可用 → 走原路径。

### Stage 3 —— 推广次序（每个点带独立验收）

注入/越狱二次把关 → CRAG per-doc / judge 五件套（省 LLM 账最直观）→ 路由&档位 → 两票预筛（误判成本最高，放最后）。

## 7. 部署形态：建议 **sidecar**，而不是塞进 backend

旧 spec 计划在 `app/services/decision_model_service.py` 里懒加载、跑在 backend 容器内。基于 §4.4 的实测，建议改为：

```
[compose] laya-decision (新增服务，独立 cpus/mem_limit)
   image: python:3.11-slim + pip install "laya[serve]==0.3.20" -i https://pypi.org/simple
   HF cache: 宿主机 hf 缓存 ro 挂载 (与 bge 同范式)
   env: LAYA_PRELOAD=1  LAYA_MODELS=laya-multilingual  LAYA_DEVICE=cpu  LAYA_THREADS=4
   expose: POST /v1/systemone  (Jev 兼容 wire)
        ↑ HTTP
[backend] decision_client.py → asyncio.wait_for(timeout) → 超时/异常 → degraded("laya_decision", e) → 走原路径
```

理由四条（都有本轮证据支撑）：
1. **资源隔离**：backend 已 `cpus: 4 / mem 10g` 且要跑 bge + OCR，mmBERT CPU 前向 190–460ms 会把主链路拖慢；
2. **依赖隔离**：transformers 将被拉到 5.17（§4.2），sidecar 可以让主后端**零依赖变更**；
3. **可独立发布/回滚**：9 天大的项目、每周几个版本、issue 158 个，必须能整体摘除；
4. **官方形态**：`laya[serve]` 本就是官方受支持的部署方式，自带 preload / threads / preload 模型选择。

若坚持嵌入 backend：至少做到 `Router(preload=True, max_loaded=1)`（避开 7.4s 切换）+ 独立线程池 +
并发护栏 2 + 1s 超时 + 整天 canary 观察 CPU steal。

## 9. 本轮重调研相对旧方案（09-21 spec）的修正

1. **修正第一段该做什么**：旧 spec 直接开工"3.5k 合成数据 + 微调 + 告警分诊"（M0+M1 = 6-7 人天才见信号）。
   → **本轮建议先做零样本 Stage 0**：用 base 已具备的通用能力（注入检测/need_retrieve）在 **2-3 人天**内验证
   "部署形态/延迟/内存/中文 routing"，拿到第一个真信号再决定投不投 Stage 1。
2. **修正 schema 里的 `score`**：旧 spec 的`severity: score(0-4)` 用了三种原语里最弱的一个
   （SST-5 0.372、社区实测全塞 medium、multilingual position bias #131）→ **改成 `choice` 五档**（"较轻/中等/较重/严重/危急"），
   需要连续量时再取 5 档的期望值，而不是直接让模型吐尔分数。
3. **修正部署位**：旧 spec 打算塞进 backend 容器 → **改为独立 sidecar `laya-serve`**，理由是
   `cpus:4 / mem 10g` 的现实容量 + dry-run 实测到的 transformers 5.x 拉取 + 项目周级迭代的可摘除性。
4. **新增依赖与源的一手实测**：PyPI requires_dist、阿里源版本滞后、torch CPU wheel 可用性、dry-run 依赖解析结果（§4）——旧版完全没有。
5. **新增原语级缺陷清单**：noul 否定敏感(#377/#156)、score position bias(#131)、confidently wrong、
   confidence 公式与 Jev 不同、checkpoint 切换 7.4s 冷代价（§3）——旧版只覆盖了"zero-shot 近随机"和"过度自信"两条。
