二、项目认知：为什么需要 RAG

2.1 业务问题

电网运维知识分散在规程、缺陷记录、检修票、厂家手册和历史问答中。通用大模型知道“常识”，却不知道企业最新的设备台账、区域规程和内部权限；直接让模型回答会产生幻觉、过期结论和无法追责的答案。

2.2 RAG 的最小闭环

用户问题 → 问题规范化/路由 → 召回候选证据 → 重排与权限过滤
→ 证据充分性检查 → 带引用生成 → 引用校验 → 记录与评测

2.3 与传统搜索、纯 LLM 的比较

方案优点风险本项目的取舍
关键词搜索可解释、速度快同义表达召回差BM25 作为稀疏通道
纯向量搜索语义泛化好数字、型号、否定词易错Embedding 双路并查
纯 LLM表达自然幻觉、知识过期必须绑定证据与拒答
混合 RAG兼顾语义与精确匹配链路复杂、需评测路由 + RRF + Rerank + CRAG

2.4 课堂演示：同一个问题的三种答案

示例问题：“10kV 线路跳闸后，现场巡视先检查哪些部位？”分别演示通用模型、关键词检索、RAG 答案，要求学员指出：是否有适用范围、是否引用原文、是否暴露文档版本与来源。

本章验收：学员能用一句话说明“RAG 不是把文档喂给模型”，而是将检索、证据治理、生成和验证组成可观测的应用链路。

三、环境搭建与服务拓扑

3.1 项目服务

前端为 Vue 3，后端为 FastAPI；数据层按职责拆分：MySQL 保存用户、文档元数据、会话与持久化缓存；Redis 保存热点缓存和运行时配置；Milvus 保存向量；Neo4j 保存实体关系；MinIO 保存原文和附件。Prometheus/Grafana 负责指标与看板。

3.2 启动清单

# 在项目根目录执行
docker compose up -d --build
docker compose ps
# 后端健康检查
curl http://127.0.0.1:8001/health
# 前端
浏览器访问 http://127.0.0.1:5173

3.3 环境变量与安全

至少配置一个模型服务密钥：DEEPSEEK_API_KEY、DASHSCOPE_API_KEY 或 ARK_API_KEY。密钥只放在本地 .env，不可提交 Git。容器内模型缓存采用离线模式时，不要把主机回环代理地址带入容器。

3.4 启动故障排查顺序

  1. 先看 docker compose ps 的健康状态。
  2. 再看 docker compose logs backend 是否为数据库、模型密钥或 Milvus 连接问题。
  3. 确认后端端口为 8001、MySQL 为 3307，避免与本机默认端口冲突。
  4. 修改后端代码或 .env 后重新构建 backend 镜像；前端页面改动可使用 Vite HMR。
讲师提示：把“能启动”作为第一个可见成果。学员如果在第一天卡在依赖安装，后续所有算法学习都会变成纸上谈兵。

四、数据与知识库

4.1 文档进入系统的生命周期

上传文件 → MinIO 保存原文 → 文档解析/清洗 → 分块与元数据
→ Embedding → Milvus 入库 → MySQL 登记版本/权限 → 可检索

4.2 分块不是“按固定字数切一刀”

规程标题、章节、表格、步骤和注意事项决定语义边界。建议保留 doc_id、chunk_idx、标题路径、设备类型、部门、版本、生效时间和 ACL。小块适合召回，大块适合给模型理解；本项目支持 small-to-big 回填父块。

4.3 双 Embedding 集合

集合维度用途注意事项
grid_chunks云模型 1024高质量语义检索切换提供商需重建集合
grid_chunks_bge本地 bge 512离线/低成本并查确保模型缓存与维度一致

4.4 MySQL 与 Redis 的教学实验

  • 建立一张 FAQ 表，记录问题、答案、关键词、版本和租户。
  • 用 BM25 对“避雷器泄漏电流异常”做关键词召回。
  • 把同一问题写入 Redis，观察命中、TTL 和失效。
  • 比较“精确缓存”和“语义缓存”的命中边界。

4.5 实训一：导入一组运维文档

每组选择 5—10 份公开或脱敏文档，设计元数据字段，导入后抽查 20 个 chunk：不得出现空文本、跨章节拼接、缺失来源或权限字段。提交《知识库质量检查表》。

五、检索工程：从召回到最终上下文

5.1 查询路由

先判断问题属于故障、规程、自然语言问答、精确型号或结构化查询。稀疏问题优先 BM25，语义问题使用向量，复杂问题走 hybrid；路由结果还会影响 topk、Milvus ef、RRF 权重和是否跳过 rerank。

5.2 混合检索主链路

query rewrite → BM25 / dense 双通道 → RRF 融合
→ rerank → tenant/ACL/docType 过滤 → MMR 去重
→ small-to-big / RAPTOR → 知识治理门禁 → 回填 chunk 元数据

5.3 为什么需要 RRF、Rerank、MMR

组件解决的问题课堂观察指标
RRF不同分数尺度无法直接相加Recall@K、来源覆盖
Rerank初召回相关但排序不准MRR、nDCG
MMR前 K 条来自同一段落、证据重复多样性、答案覆盖
ACL 过滤用户不应看到其他部门文档越权用例 0 命中

5.4 实训二：检索对比实验

准备 30 条黄金问题，分别运行 sparse、dense、hybrid 三种策略，记录 Recall@5、首 token 延迟和平均上下文长度；再打开 rerank/MMR，对比指标变化。禁止只凭“感觉更好”下结论。

代码走读位置：backend/app/services/retrieval_service.py::mixed_search、backend/app/rag/rrf.py、backend/app/rag/mmr.py、backend/app/routing/routing_service.py。

六、问答增强：让答案可控、可证据化

6.1 多轮问题与 Query 改写

“它为什么又跳了？”不能直接拿去检索。系统将会话历史压缩为独立检索问题，但原始问题仍用于最终回答，避免改写后的关键词破坏用户意图。课堂要求学员展示改写前后文本，并检查是否引入了不存在的设备。

6.2 CRAG 自纠错

召回结果会进行证据充分性判断：正确则生成，模糊则扩展邻近块，不正确则强制改写并重检索；仍不可靠时保守拒答。拒答是安全策略，不是系统失败。

6.3 GraphRAG 与结构化事实

Neo4j 适合回答“设备—位置—关系—历史事件”的多跳问题。图谱上下文应与文本证据并列呈现，并保留来源和时间，防止把推断关系冒充原文事实。

6.4 三级缓存

单轮问题：L1 Redis → L2 MySQL → L1.5 Semantic Cache → LLM
高置信结果：MySQL 持久化后写 Redis，再写语义索引
多轮对话：不写三层问答缓存，避免上下文污染
语义开关、引用校验开关变化：进入 cache version，旧缓存自动隔离

6.5 引用与答案质量

答案中的引用必须能映射到实际 chunk；系统还可做句子—证据相似度校验，并异步执行 NLI 回填。课堂演示“引用不存在、引用错段、引用与结论矛盾”三种反例，要求学员判断应删除结论、重检索还是拒答。

实训三：安全回答器：为 10 条问题设置“证据充足 / 证据模糊 / 无证据”三类预期，验收输出必须包含答案、来源、置信度和必要的风险提示。

七、应用开发：FastAPI、Vue、SSE 与权限

7.1 后端分层原则

Router 只负责参数、权限与响应；业务编排放在 services；算法放在 rag/routing；外部模型和数据库通过 providers/clients 访问。外部调用失败要记录 DEGRADED 指标并降级，不能用空的 except 静默吞错。

7.2 问答接口课堂演示

# OpenAPI 文档
http://127.0.0.1:8001/docs

# 典型链路
POST /api/qa/answer          # 普通 JSON
POST /api/qa/answer/stream   # SSE 流式输出
GET  /api/retrieval/debug    # 查看召回与路由轨迹

7.3 SSE 事件讲解

前端依次接收 meta、若干 token、引用/质量信息和 done。网络中断、重复 token、done 丢失都要有可恢复策略；UI 不能把“正在生成”误显示为最终答案。

7.4 Vue 页面实训

以 Chat.vue 为入口，增加“查看证据”抽屉：显示 query、路由、召回来源、分数、引用校验状态和耗时。再在 Documents.vue 中补充文档版本和权限标签。

7.5 RBAC 与租户隔离

前端按钮隐藏只是体验层，后端路由必须使用 require_perm，并在文档、检索、图谱、预览、缓存查询中持续传递 tenant 与 ACL。设计一个“普通运维员不能看检修票原文”的越权测试。

八、评测、可观测性与上线

8.1 评测四层

层次核心问题建议指标
数据层文档能否被正确解析、分块、索引？空块率、重复率、覆盖率
检索层正确证据是否进入 Top-K？Recall@K、MRR、nDCG
生成层答案是否正确、完整、可引用？Faithfulness、Answer Relevancy、引用通过率
系统层是否快、稳、可追责？首 token、P95、错误率、成本、缓存命中率

8.2 黄金集构造

每条样本至少包含：问题、问题类型、期望证据 doc/chunk、参考答案、是否允许拒答、租户/角色。覆盖精确型号、同义表达、否定条件、多轮指代、无答案和越权问题。黄金集必须版本化，变更要写明原因。

8.3 运行观测

Prometheus 记录检索、缓存、CRAG、引用和模型调用指标；Grafana 用于趋势观察；Langfuse/OTEL 用于单次链路追踪。课堂要求从一次低质量回答反查：路由是否偏、召回是否漏、重排是否错、模型是否越过证据。

8.4 上线检查单

  • 模型密钥、数据库密码、JWT 密钥均来自安全配置。
  • 后端代码或配置变更后完成对应镜像重建。
  • 数据库迁移、Milvus 集合维度和备份恢复演练通过。
  • 权限、拒答、引用格式、过期文档门禁均有自动化用例。
  • 健康检查、日志、指标、告警和回滚步骤写入部署手册。

改动边界：练习只能在 router、service、rag、前端 view 的既有边界内完成；不要把检索逻辑塞进 router，也不要绕过权限过滤直接查数据库。

十二、知识库建设标准作业流程（SOP）

12.1 文档接收

  1. 登记文档名称、来源部门、负责人、版本、生效日期和保密等级。
  2. 检查文件是否可复制、是否包含扫描图片、表格和页眉页脚。
  3. 为每份文档生成唯一 doc_id，原文存入 MinIO。

12.2 清洗与分块

  1. 去除重复页眉、页脚、目录和无意义空白。
  2. 标题必须进入 chunk 的 metadata，不要只保留正文。
  3. 步骤、条件、例外、警告尽量保持在同一 chunk。
  4. 对表格保留列名，并将单位、上下限和适用设备写入文本。
  5. 给 chunk 增加版本、租户、部门、允许角色和父块标识。

12.3 入库验收

检查项最低标准不合格处理
空文本0%回到解析阶段
来源字段100%禁止发布
权限字段100%进入隔离区
向量维度与集合一致停止批量写入
版本状态只能有一个当前版本走知识治理流程

12.4 版本与撤回

新规程上线不能简单覆盖旧文档。应保留旧版本、标记生效时间，并在检索阶段由知识治理门禁排除已撤回、已替代或过期文档。任何文档撤回都应能追溯到操作人和原因。

十三、检索调参实验手册

13.1 单变量实验原则

一次只改变一个开关或参数，固定模型、数据集、问题顺序和随机种子。每次实验保存配置快照、指标、失败样本和结论，避免“多个开关一起打开后不知道谁有效”。

13.2 推荐实验矩阵

实验基线变量观察
ABM25dense语义召回是否补足同义问题
Bdensehybrid + RRF型号、数值问题是否提升
CTop-K 排序Rerank前 3 条证据是否更相关
DRerankMMR重复证据是否减少
E普通生成CRAG无证据问题是否更少幻觉
F无缓存三级缓存延迟、命中率与新鲜度变化

13.3 失败样本分类

  • 召回失败：正确文档未进入候选集，优先检查分块、同义词、路由和 embedding。
  • 排序失败：正确文档在候选集但排名靠后，检查 rerank、RRF 权重和元数据过滤。
  • 生成失败：证据正确但答案错误，检查 prompt、上下文长度和引用约束。
  • 治理失败：引用过期或越权文档，检查版本门禁、ACL 和缓存隔离。
  • 系统失败：超时、断流、降级不明显，检查外部调用、限流和 DEGRADED 指标。

十四、故障演练与标准答案

14.1 Milvus 连接失败

现象：上传成功但问答没有召回。
排查：检查容器健康、端口 19530、集合名称和向量维度；查看 backend 日志中的 degraded 标签。
合格处理：系统给出可识别的降级提示，不伪装成“没有相关知识”。

14.2 缓存返回旧规程

现象：文档已更新，答案仍引用旧版本。
排查：核对 cache key 是否包含 citation cache version、文档治理代次和租户；清理或自然淘汰旧缓存后复测。
合格处理：新旧版本不会因缓存键相同而混用。

14.3 检索结果越权

现象：普通角色在调试接口看到其他部门 chunk。
排查：确认后端 ACL 过滤而非只依赖前端隐藏；检查 doc_id、tenant_id、allowed_roles 是否同时生效。
合格处理：越权请求返回空证据或业务拒绝，且留下审计日志。

14.4 流式回答卡住

现象：页面一直显示“生成中”。
排查：检查 SSE 心跳、异常事件、done 事件、浏览器断线重连和代理缓冲。
合格处理：用户看到明确失败状态，可重试，后台日志保留 request_id。

正课内容

1.1 什么是 RAG

RAG = Retrieval-Augmented Generation（检索增强生成）。

传统大模型的问题：

  • 秒级返回答案。
  • 减少翻阅 PDF 的时间。

第 4 章：FastAPI 基础与项目应用

4.1 什么是 FastAPI

FastAPI 是一个现代、高性能的 Python Web 框架，基于：

  • Starlette：提供 ASGI 支持和请求生命周期。
  • Pydantic：提供数据校验和序列化。
  • 类型注解：自动生成 API 文档。

它的核心优势：

  1. 异步原生：所有路由可以是 async def。
  2. 自动文档：访问 /docs 得 Swagger UI。
  3. 依赖注入：通过 Depends 管理权限、数据库 session 等。
  4. 高性能：基于 Starlette 和 uvicorn，性能接近 Node.js/Go。

4.2 最小 FastAPI 示例

from fastapi import FastAPI

app = FastAPI()

@app.get("/")
async def root():
    return {"message": "Hello World"}

运行：

uvicorn main:app --reload

访问 http://127.0.0.1:8000/docs 即可看到 API 文档。

4.3 项目入口 main.py

打开 backend/app/main.py，核心是创建 FastAPI 实例和 lifespan：

app = FastAPI(
    title=settings.APP_NAME,
    version=settings.APP_VERSION,
)

@asynccontextmanager
async def lifespan(app: FastAPI):
    # 启动时：初始化日志、数据库、Milvus、Redis、Neo4j 等
    setup_logging()
    await init_db()
    await ensure_collections()
    start_background_loops()
    yield
    # 关闭时：清理资源

lifespan 是 FastAPI 提供的应用生命周期钩子。yield 之前的代码在启动时执行，之后的代码在关闭时执行。

4.4 Router 模式

项目没有把所有路由写在一个文件，而是拆成多个 router：

# backend/app/routers/qa.py
from fastapi import APIRouter

router = APIRouter(prefix="/qa", tags=["问答"])

@router.post("/answer")
async def answer(req: QuestionRequest):
    ...

注册 router：

# backend/app/main.py
from app.routers import qa, document, system

app.include_router(qa.router, prefix="/api")
app.include_router(document.router, prefix="/api")
app.include_router(system.router, prefix="/api")

最终 /qa/answer 的实际路径是 /api/qa/answer。

4.5 请求与响应模型

from pydantic import BaseModel

class QuestionRequest(BaseModel):
    question: str
    stream: bool = False

@router.post("/answer")
async def answer(req: QuestionRequest):
    return {"question": req.question}

FastAPI 会自动：

  1. 把 JSON body 转成 QuestionRequest。
  2. 校验字段类型（缺少 question 会返回 422）。
  3. 把返回值转成 JSON。
  4. 在 Swagger 上显示参数说明。

4.6 依赖注入 Depends

Depends 让代码更干净。例如获取当前用户：

from fastapi import Depends

async def get_current_user(token: str = Depends(oauth2_scheme)):
    ...

@router.get("/me")
async def me(user: User = Depends(get_current_user)):
    return user

项目中的权限依赖：

@router.post("/answer")
async def answer(user=Depends(require_perm("qa:answer"))):
    ...

require_perm("qa:answer") 返回一个依赖函数，检查用户是否有"qa:answer"权限。

4.7 同步 vs 异步路由

FastAPI 支持两种写法：

# 同步：会用线程池执行
def sync_route():
    return {"msg": "sync"}

# 异步：事件循环直接调度
async def async_route():
    await asyncio.sleep(1)
    return {"msg": "async"}

项目中大量使用异步，因为数据库、缓存、外部 API 调用都是 IO 密集型。

第 5 章：Pydantic——配置与数据校验

5.1 什么是 Pydantic

Pydantic 是 Python 的类型校验库。你定义一个类，它自动帮你：

  • 校验输入数据类型。
  • 提供自动补全和 IDE 支持。
  • 把对象序列化成 JSON。

例如：

from pydantic import BaseModel

class User(BaseModel):
    name: str
    age: int

u = User(name="Alice", age="30")  # 自动把 "30" 转成 int
print(u.model_dump())  # {'name': 'Alice', 'age': 30}

5.2 FastAPI 中的请求校验

项目里的 schema 都用 Pydantic：

# backend/app/schemas/qa.py
class QuestionRequest(BaseModel):
    question: str
    conversation_id: Optional[str] = None
    stream: bool = False
    regen: bool = False

当前端发送：

{"question": "倒闸操作是什么？", "stream": true}

FastAPI 自动校验并转成 Python 对象。如果 question 缺失，返回：

{"detail": [{"loc": ["body", "question"], "msg": "field required", "type": "value_error.missing"}]}

5.3 项目配置 Settings

from pydantic_settings import BaseSettings, SettingsConfigDict

    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        extra="ignore",
        case_sensitive=False,

    APP_NAME: str = "电网运维 RAG"
    BACKEND_PORT: int = 8001
    LLM_PROVIDER: str = "deepseek"

读取顺序：

  1. 环境变量
  2. .env 文件
  3. 字段默认值

第 6 章：SQLAlchemy 2.0 异步数据库

6.1 什么是 ORM

ORM（Object-Relational Mapping）让你用 Python 类来操作数据库表，不用手写 SQL。

例如：

class User(Base):
    __tablename__ = "user"
    id = Column(Integer, primary_key=True)
    username = Column(String(255))

对应 SQL：

CREATE TABLE user (
    id INT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(255)
);

6.2 SQLAlchemy 2.0 新语法

项目使用 SQLAlchemy 2.0 的 Mapped 语法，更类型安全：

from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column
from sqlalchemy import String

class Base(DeclarativeBase):
    pass

class Document(Base):
    __tablename__ = "document"

    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(255))
    status: Mapped[str] = mapped_column(String(50), default="active")
    tenant: Mapped[str] = mapped_column(String(64), index=True)

6.3 模型关系

一对多关系：

class Document(Base):
    id: Mapped[int] = mapped_column(primary_key=True)
    chunks: Mapped[List["Chunk"]] = relationship("Chunk", back_populates="document")

class Chunk(Base):
    id: Mapped[int] = mapped_column(primary_key=True)
    document_id: Mapped[int] = mapped_column(ForeignKey("document.id"))
    document: Mapped["Document"] = relationship("Document", back_populates="chunks")

6.4 异步 Session

项目使用 aiomysql + SQLAlchemy 异步：

# backend/app/db/session.py
from sqlalchemy.ext.asyncio import create_async_engine, AsyncSession, async_sessionmaker

DATABASE_URL = "mysql+aiomysql://grid:grid123456@mysql:3306/grid_qa?charset=utf8mb4"
engine = create_async_engine(DATABASE_URL)

async_session = async_sessionmaker(engine, class_=AsyncSession, expire_on_commit=False)

async def get_session() -> AsyncGenerator[AsyncSession, None]:
    async with async_session() as session:
        yield session

在 router 中使用：

@router.get("/documents")
async def list_docs(session: AsyncSession = Depends(get_session)):
    result = await session.execute(select(Document))
    return result.scalars().all()

7.1 Vue 3 核心变化

第 11 章：Embedding 与向量检索

11.1 什么是 Embedding

Embedding 是把文本、图片等数据转换成稠密向量的技术。语义相近的内容，向量空间中的距离也近。

例如：

  • "主变重瓦斯动作" 和 "变压器瓦斯保护跳闸" → 向量距离近。
  • "主变重瓦斯动作" 和 "今天天气很好" → 向量距离远。

11.2 Embedding 模型

doubao-embedding 1024 云 备用

11.3 向量检索原理

把文档 chunk 转成向量存入 Milvus。用户提问时，把问题也转成向量，然后在 Milvus 中找最近的向量。

常用距离：

  • 余弦相似度：方向越接近越相似。
  • 欧氏距离：距离越短越相似。

第 12 章：BM25 稀疏检索

12.1 为什么需要 BM25

向量检索擅长语义匹配，但不擅长精确匹配专业术语和标准号。例如：

"DL/T 596-2021 对变压器油色谱的要求？"

12.2 BM25 原理

BM25 是一种基于词频的排序算法，综合考虑：

  • 词在文档中的出现次数（TF）。
  • 词在所有文档中的出现频率（IDF）。
  • 文档长度归一化。

第 13 章：RRF 多路召回融合

13.1 为什么需要多路融合

单路检索有局限：

  • 向量检索：语义好，但可能漏掉专业术语。
  • BM25：精确匹配好，但无法理解语义。
  • bge 本地：便宜离线，但效果可能稍差。

多路融合可以取长补短。

13.2 RRF 公式

RRF（Reciprocal Rank Fusion）：

RRF_score(d) = Σ 1 / (k + rank_i(d))
  • k：平滑常数，项目默认 60。
  • rank_i(d)：文档 d 在第 i 路中的排名。

13.3 项目中的 RRF

# backend/app/rag/rrf.py
def rrf_fuse(lists, k=60, weights=None):
    scores = {}
    for i, ranked_list in enumerate(lists):
        weight = weights[i] if weights else 1.0
        for rank, doc_id in enumerate(ranked_list):
            scores[doc_id] = scores.get(doc_id, 0) + weight / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)

第 14 章：Rerank 与 MMR

14.1 Rerank 的作用

RRF 融合后，候选 chunk 的排名可能还不够精准。rerank 用更强大的模型直接判断"这个 chunk 对回答 query 有多重要"。

14.2 Rerank 模型

项目常用 gte-rerank-v2 等云端 rerank 模型。输入 query + chunk，输出相关性分数。

14.3 降级策略

rerank 是外部调用，可能超时或失败。项目降级策略：

async def rerank(query, candidates):
    try:
        return await cloud_rerank(query, candidates)
    except Exception as e:
        obs.degraded("rerank", e)
        return candidates  # 回退到 RRF 原序

14.4 MMR 多样性

rerank 后 topK 可能内容重复。MMR 平衡相关性和多样性：

MMR_score = λ * Sim(query, doc) - (1-λ) * max Sim(doc, selected_docs)
  • λ=1：只看相关性。
  • λ=0：只看多样性。
  • 项目默认 MMR_LAMBDA=0.5。

第 15 章：CRAG 自纠错

15.1 为什么需要 CRAG

大模型可能会编造答案。CRAG 在生成前检查检索到的证据是否足够可信，不够就重写 query 再检索，还不够就拒答。

15.2 三档分级

档位 条件 动作
correct top1 score >= CRAG_HIGH 证据充分，继续生成
ambiguous CRAG_LOW <= top1 < CRAG_HIGH 证据一般，生成但降低置信度
incorrect top1 < CRAG_LOW 改 query 重检索；仍不足则拒答

默认阈值：CRAG_HIGH=0.72，CRAG_LOW=0.3。

15.3 项目实现

# backend/app/rag/crag.py
@dataclass
class GradeResult:
    action: str
    confidence: float
    top_score: float

def grade(contexts, query) -> GradeResult:
    top_score = contexts[0].score if contexts else 0
    if top_score >= settings.CRAG_HIGH:
        return GradeResult("correct", 0.9, top_score)
    elif top_score >= settings.CRAG_LOW:
        return GradeResult("ambiguous", 0.6, top_score)
    else:
        return GradeResult("incorrect", 0.3, top_score)

23.1 retrieval_service.mixed_search

async def mixed_search(query, route, user, top_k=10):
    # 1. 并行执行多路检索
    dense_results = await dense_search(query)
    sparse_results = await bm25_search(query)
    bge_results = await bge_search(query)

    # 2. RRF 融合
    fused = rrf_fuse([dense_results, sparse_results, bge_results])

    # 3. rerank
    reranked = await rerank(query, fused)

    # 4. MMR 去重
    diverse = mmr_diverse(reranked)

    # 5. ACL 过滤
    return filter_by_acl(diverse, user)

电网运维 RAG 智能问答系统是一个面向电力行业（变电、配电、输电）的智能问答平台，基于大语言模型（LLM）+ 检索增强生成（RAG）技术，为一线运维人员提供故障处理、规程查询、设备状态分析等场景的可信答案。

  • 可进化：知识自进化、证据缺口补全、用户反馈闭环。
  • 强合规：RBAC + 多租户 + 文档级 ACL + 操作审计。

3.4.4 CRAG 自纠错（rag/crag.py）

crag.grade() 基于 rerank top1 分数做三档分级：

档位 条件 动作
correct top1 score >= CRAG_HIGH (0.72) 证据充分，进入生成
ambiguous CRAG_LOW (0.3) <= score < CRAG_HIGH 证据一般，可进入生成但置信度降低
incorrect score < CRAG_LOW 触发 query 改写重检索；仍不足则 refused

当 CRAG_V3_ENABLE=True 时，升级为连续置信度 5 档 + 归因矩阵。

当 CRAG_PERDOC_ENABLE=True 时，rag/crag_v2.py 调用 LLM 逐条评估每篇文档相关性。

3.4.5 引用校验（rag/citation*.py）

引用系统四层架构：

层级 文件 功能 开关
L1 格式校验 citation_verifier.py 检查角标格式、编号连续性 CITATION_VERIFIER_ENABLE
L2 向量校验 citation_verifier.py 答案句与原文 chunk 向量相似度 CITATION_VERIFIER_ENABLE
L3 NLI 校验 citation_verifier.py 自然语言推理判断句是否被 chunk 支撑 CITATION_NLI_ENABLE
自动补标 citation.py 无角标句子按向量相似度自动补引用 CITATION_AUTO_ENABLE

当校验失败且 CITATION_REWRITE_ON_FAIL=True 时，联动 CRAG 做二次检索或 refused。

11. 关键设计约定

11.1 降级而非崩溃

  • 所有外部调用必须包 try/except。
  • 失败调用 core/obs.degraded(name, exc, msg)。
  • 禁止裸 except: pass。

11.2 响应约定

  • BizError → HTTP 200，业务错误通过 body {code, message, data} 返回。
  • 成功：{"code": 0, "message": "ok", "data": ...}
  • 失败：{"code": 非0, "message": "错误信息", "data": null}

11.3 路由约定

  • routers/ 保持薄：参数校验 + require_perm + 调 service + 写操作日志。
  • 新增功能：逻辑进 services/，路由只转发。

11.4 缓存版本

  • 所有影响答案语义的开关必须加入 citation_cache_version()。
  • 治理态变（withdraw/supersede/expire）会 bump _gov_generation，使缓存失效。

11.5 多租户与 ACL

  • tenant 贯穿检索、缓存、图谱、预览、文档 ACL。
  • 文档 ACL：按 dept / role / tenant 过滤。
  • 前端 utils/perm.js 仅做按钮隐藏，不是安全边界。

11.6 双 Embedding Collection

  • grid_chunks（1024d，云）与 grid_chunks_bge（512d，本地）独立 collection。
  • DOC_SIZE_THRESHOLD=5000 决定单篇文档走云还是本地 bge。
  • 切换 provider / 维度必须重建 collection。

11.7 容器构建注意

  • backend 源码 bake 进镜像，改代码/改 .env 后需重建容器。
  • 容器内 HF_HUB_OFFLINE=1，挂载宿主机 HF 缓存只读。
  • 容器内不设 HTTPS_PROXY（宿主机代理仅回环）。
  • bge 启动期预热较慢，健康检查可能暂时为空。

11.8 代码风格

  • 异步优先；snake_case 文件/函数，PascalCase 模型/schema。
  • Lint：ruff check backend tests。
  • 提交：Conventional Commits（feat(scope): ...）。

11.9 安全红线

  • 不提交真实 API Key。
  • Grafana webhook token 必须独立配置，不复用内置值。
  • 实时事件接入凭据按租户隔离。

12. 常见问题排查

12.1 "改了代码没生效"

backend 源码 bake 进镜像，需重建：

docker compose up -d --build backend

12.2 缓存不命中

检查：

  1. 是否多轮对话（多轮不走缓存）。
  2. citation_cache_version() 是否变化导致 key 变化。
  3. Redis 是否命中但文档已被治理撤回。
  4. SEMANTIC_CACHE_ENABLE 是否开启。

12.3 检索结果差

排查路径：

  1. /api/retrieval/debug-search 查看每步中间结果。
  2. 检查 routing_decision.route 是否合理。
  3. 检查 RRF 权重、rerank 是否降级、MMR λ。
  4. 检查 ACL 是否误过滤。

12.4 LLM 返回空答案

检查：

  1. LLM_FALLBACK_ON_EMPTY=True 是否生效。
  2. llm_router 熔断状态。
  3. DeepSeek reasoning_effort 是否耗尽预算。

12.5 Milvus 写入失败

常见原因：

  1. MinIO 磁盘水位满 → datanode panic。
  2. etcd 或 milvus-minio 未健康启动。
  3. collection schema 与 embedding 维度不匹配。

12.6 Neo4j 启动失败

可能因断电导致事务日志损坏，已配置：

NEO4J_internal_dbms_tx__log_fail__on__corrupted__log__files=false
NEO4J_db_recovery_fail__on__missing__files=false

如仍失败，可从 MySQL KgTriple 镜像重建：

python scripts/rebuild_kg_from_mysql.py

### 3.1 智能路由(6 维特征决策树)

> 用 6 维查询特征(<1ms)自动选检索路径,**60%+ 查询跳过冗余分支,p95 检索延迟降 30-50%**。低于 `min_confidence=0.6` 自动升级 hybrid 保召回。

```mermaid

    classDef feat fill:#e3f2fd,stroke:#1976d2
    classDef dec fill:#fff8e1,stroke:#f9a825,stroke-width:2px
    classDef out fill:#e8f5e9,stroke:#2e7d32

    Q([用户 query]):::feat

    DT -- "故障口语/同义词<br/>(如 跳闸/发烫)" --> DN["dense<br/>仅向量召回"]:::out
```

## 四、RAG 核心·增强 Augmentation

> **增强的底层逻辑**:在「检索到结果」和「交给 LLM 生成」之间,插入**缓存复用 + 自纠错 + 证据缺口闭环 + prompt 工程**,把"一次性管道"升级为"可信、高效、自进化"的闭环。

## 十五、FAQ

**Q: Rerank 用的是什么?**
A: 阿里百炼 DashScope `gte-rerank-v2`(原生 HTTP API),非本地 bge-reranker。失败降级回退 RRF,`DEGRADED{tag=rerank}` 可观测。

**Q: 双 Embedding 是二选一吗?**
A: 不是。写入时按文档字数(>5000 走云 1024d / ≤5000 走 bge 512d)路由到不同 collection;**检索时 `asyncio.gather` 并查两个 collection** 融合,既绕云限流又覆盖不同向量空间。

**Q: docType 过滤在哪做?**
A: 检索**后置过滤**——先 RRF+rerank 出 pool,再查 MySQL Document 表按 tenant/docType/equipment/ACL 过滤(非 Milvus 标量过滤),docType 无条件补全到每条用于来源卡片。

**Q: GraphRAG 在检索哪一步?**
A: 在 `mixed_search` 文档检索**之后**、CRAG 纠错**之后**,由 `qa_service.answer:351` 单独调用 `kg_service.graph_context`,结果与文档分块**并列**进 prompt。Neo4j 不可用时回退 MySQL KgTriple 表。

**Q: 多轮问答为什么有时不命中缓存?**
A: 多轮**不写缓存**(仅高置信时读 Redis 热点),防跨对话脏命中;且检索用 standalone 消解后的 query,消解后 `search_q != nq` 时不读。

**Q: pymilvus 为什么用 2.4?**
A: 2.3 的 grpcio 在 Python 3.13 Windows 无预编译 wheel。另需 `setuptools<81`(pymilvus 用 pkg_resources,≥81 已移除)。

**Q: PaddleOCR 为什么用 rapidocr-onnxruntime?**
A: paddlepaddle 3.3.1 在 Windows 有 onednn PIR bug。rapidocr 用 PP-OCR 官方模型 + onnxruntime 后端,效果等同、规避 bug。

**Q: bge 模型下载失败?**
A: 设 `HF_ENDPOINT=https://hf-mirror.com` 或 `HTTPS_PROXY`,或预下到 HF 缓存(发行包已含 `data/hf-cache` 零下载)。
