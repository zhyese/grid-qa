# 电网运维 RAG 智能问答系统 — 功能完成度审计与增量机会调研 v6

> **版本:** v6.0 | **日期:** 2026-10-04 | **基准:** v5 报告（2026-10-01）+ 六项功能落地（commit 72caf25..2c85bd2）之后的**完成度审计**
> **方法:** 三路并行代码审计（开关接线完整度 / 前后端覆盖差集 / 半成品与占位标记）+ `.env` 运行态核对 + `reports/` 评测产出盘点
> **与前几轮的区别:** v1-v5 都是"向外找新机会"，本轮是"向内找没做完的"——先把已建成的能力收口，再谈新增。

---

## 一、执行摘要

"感觉好多功能没做全"的直觉**基本正确**，但缺口不在代码量，而在三层收口：

1. **第一层：开闸与验收欠账（最紧迫、成本最低）**。代码全部落地但运行环境关着：刚落的六项功能在 `.env` 里 5 项未开（F1/F2/H2/F7/H6），`CRAG_V3/CRAG_PERDOC` 只翻了 `.env.example`、真实 `.env` 与 `config.py` 默认值都没收口（等于新常态的核心 CRAG v3 实际没开）；H1 换 v4 后的检索验收无产出（`reports/eval_retrieval` 最新停在 2026-08-06）。**约 1 人天即可把已付费的能力全部点亮。**
2. **第二层：最后一公里缺口（约 10 项，~2 周）**。后端完整、前端零入口的成块能力（文档版本/回滚/块编辑/查重、插件注册表、治理传播执行）；注释里写着"后续"的占位（RBAC DB 覆盖、C3 治理度量埋点、Nacos 配置监听、高频问答对接主链路）；前端自写布局与后端 layout 接口的双轨（数字孪生）；18 个死 api wrapper。每项都有现成后端，缺的只是收口。
3. **第三层：已调研未落地 backlog（v4 的 G1-G7、v5 的 H3-H5、方向 2/5/7/8、Laya）**。本轮用审计证据重排了优先级：G3（可信闭环）和 H4（真实遥测）因 F1/F2 的落地而**前置条件变成熟**，升为下一批首选。

**开关体检结论：50 个休眠开关，45 个"完整休眠"（实现+测试齐，纯待开闸），5 个半接线（只缺测试），0 个死开关，93 个 service 无孤儿**——这个仓库的欠账形态是"收口"，不是"返工"。

## 五、建议路线（两周视角）

1. **第 1 周：收口批（P0 全部 + P1-5/6/7）**——点亮六项功能、清评测欠账、文档资产页、F2 数据通道、孪生布局归一。全部是"把已建成的接上"，无新架构风险。
2. **第 2 周起：合规批（G1+G3+G7，v4 建议的原批）**——F1 通道让 G3 少一半工作量；H4 Stage 0 与 VLM 开闸作穿插（各 ≤2 天，独立可回滚）。
3. **纪律**：每开一个休眠开关，跑一次 eval_matrix 对应维度（verdict 仅建议、不自动翻转——沿用既有红线）；新常态进 config.py 前先跑测试对照。

## 六、不建议追

- 为 50 个开关逐个造管理 UI——开闸决策走 eval_matrix verdict + P0-3 的轻量 feature-flags 端点即可；
- 把 fault_prediction 升级成"真模型"——数据（真实遥测）没进来之前是伪需求，先做 H4；
- 继续叠 RAG 技巧（MULTI_QUERY/SELF_RAG 已被能力收益矩阵判为回收候选，不再投入）；
- 业务外延赛道（延续 v4/v5 负清单）。
