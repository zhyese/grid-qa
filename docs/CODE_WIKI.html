1. 项目概述

1.1 项目定位

电网运维 RAG 智能问答系统是一个面向电力行业（变电、配电、输电）的智能问答平台，基于大语言模型（LLM）+ 检索增强生成（RAG）技术，为一线运维人员提供故障处理、规程查询、设备状态分析等场景的可信答案。

核心设计目标：

  • 高可信：通过 CRAG 自纠错、引用校验、LLM-judge 降低幻觉。
  • 高可用：所有外部依赖故障降级，不阻塞主链路。
  • 可观测：Prometheus/Grafana/Langfuse 全链路监控。
  • 可进化：知识自进化、证据缺口补全、用户反馈闭环。
  • 强合规：RBAC + 多租户 + 文档级 ACL + 操作审计。

1.2 业务场景

场景 示例问题 涉及能力
故障处理 "110kV 主变重瓦斯动作如何处理？" 路由 → 混合检索 → CRAG → 图谱 → 生成
规程查询 "倒闸操作的安全组织措施有哪些？" BM25 + 向量检索 → 引用校验

2.2 请求全生命周期

一次问答请求 POST /api/qa/answer 的完整处理流程：

# 阶段 核心文件 关键动作
1 接入 routers/qa.py JWT 校验、qa:answer 权限、限流、创建 trace collector。
2 预处理 services/qa_service.py query 归一化、safety.guard_query 注入检测。
3 缓存 services/qa_service.py L1 Redis → L2 MySQL → L1.5 Semantic；命中则复核知识时效。
4 多轮消解 services/standalone_query.py 基于会话历史改写成独立查询，仅用于检索。
5 智能路由 routing/routing_service.py 6 维特征 → sparse / dense / hybrid / sparse_first。
6 混合检索 services/retrieval_service.py 双路向量 + BM25 → RRF → rerank → MMR → small-to-big → ACL。
7 CRAG 自纠错 rag/crag.py / rag/crag_v2.py correct/ambiguous/incorrect 分级，触发改写重检索或拒答。
8 图谱增强 services/kg_service.py Neo4j 多跳补全设备-故障-处置结构化上下文。
9 LLM 生成 providers/llm_router.py turbo/plus 分档 → fallback 链 → 流式生成 → PII 脱敏。
10 引用校验 rag/citation.py + rag/citation_verifier.py 自动补标 + 格式/向量/NLI 三层校验。
11 落库缓存 services/qa_service.py 保存会话、高置信写入缓存、记录成本与在线 eval。
12 异步闭环 services/knowledge_evolution_service.py LLM-judge、证据缺口收集、dislike 沉淀。

3.4.4 CRAG 自纠错（rag/crag.py）

crag.grade() 基于 rerank top1 分数做三档分级：

档位 条件 动作
correct top1 score >= CRAG_HIGH (0.72) 证据充分，进入生成
ambiguous CRAG_LOW (0.3) <= score < CRAG_HIGH 证据一般，可进入生成但置信度降低
incorrect score < CRAG_LOW 触发 query 改写重检索；仍不足则 refused

当 CRAG_V3_ENABLE=True 时，升级为连续置信度 5 档 + 归因矩阵。

当 CRAG_PERDOC_ENABLE=True 时，rag/crag_v2.py 调用 LLM 逐条评估每篇文档相关性。

3.4.5 引用校验（rag/citation*.py）

引用系统四层架构：

层级 文件 功能 开关
L1 格式校验 citation_verifier.py 检查角标格式、编号连续性 CITATION_VERIFIER_ENABLE
L2 向量校验 citation_verifier.py 答案句与原文 chunk 向量相似度 CITATION_VERIFIER_ENABLE
L3 NLI 校验 citation_verifier.py 自然语言推理判断句是否被 chunk 支撑 CITATION_NLI_ENABLE
自动补标 citation.py 无角标句子按向量相似度自动补引用 CITATION_AUTO_ENABLE

当校验失败且 CITATION_REWRITE_ON_FAIL=True 时，联动 CRAG 做二次检索或 refused。

5.2 缓存三级架构

L1 Redis（热点）
    ├── hotqa:{nq}                 # 用户 like 的高频问答，永不过期
    └── qa:{tenant}:{nq_hash}:{cv} # TTL 3 天
L2 MySQL（持久）
    └── qa_cache 表                # Write-Through，Redis LRU 淘汰后备
L1.5 Semantic（语义相似）
    └── semantic:{tenant}:{embedding_hash}

缓存命中规则：

  • 仅单轮问答走缓存；多轮跳过。
  • 命中后调用 _cache_knowledge_valid() 复核文档是否被撤回/过期。
  • 缓存 key 包含 citation_cache_version()，开关变化自动失效。

5.3 双 Embedding Collection

Collection 维度 Provider 用途
grid_chunks 1024 云（qwen/doubao） 大文档（>5000 字）
grid_chunks_bge 512 本地 bge-small-zh-v1.5 小文档、离线环境
memory_collection - 云/本地 Agent 长期记忆

切换 embedding provider 或维度必须重建 collection。

11. 关键设计约定

11.1 降级而非崩溃

  • 所有外部调用必须包 try/except。
  • 失败调用 core/obs.degraded(name, exc, msg)。
  • 禁止裸 except: pass。

11.2 响应约定

  • BizError → HTTP 200，业务错误通过 body {code, message, data} 返回。
  • 成功：{"code": 0, "message": "ok", "data": ...}
  • 失败：{"code": 非0, "message": "错误信息", "data": null}

11.3 路由约定

  • routers/ 保持薄：参数校验 + require_perm + 调 service + 写操作日志。
  • 新增功能：逻辑进 services/，路由只转发。

11.4 缓存版本

  • 所有影响答案语义的开关必须加入 citation_cache_version()。
  • 治理态变（withdraw/supersede/expire）会 bump _gov_generation，使缓存失效。

11.5 多租户与 ACL

  • tenant 贯穿检索、缓存、图谱、预览、文档 ACL。
  • 文档 ACL：按 dept / role / tenant 过滤。
  • 前端 utils/perm.js 仅做按钮隐藏，不是安全边界。

11.6 双 Embedding Collection

  • grid_chunks（1024d，云）与 grid_chunks_bge（512d，本地）独立 collection。
  • DOC_SIZE_THRESHOLD=5000 决定单篇文档走云还是本地 bge。
  • 切换 provider / 维度必须重建 collection。

11.7 容器构建注意

  • backend 源码 bake 进镜像，改代码/改 .env 后需重建容器。
  • 容器内 HF_HUB_OFFLINE=1，挂载宿主机 HF 缓存只读。
  • 容器内不设 HTTPS_PROXY（宿主机代理仅回环）。
  • bge 启动期预热较慢，健康检查可能暂时为空。

11.8 代码风格

  • 异步优先；snake_case 文件/函数，PascalCase 模型/schema。
  • Lint：ruff check backend tests。
  • 提交：Conventional Commits（feat(scope): ...）。

11.9 安全红线

  • 不提交真实 API Key。
  • Grafana webhook token 必须独立配置，不复用内置值。
  • 实时事件接入凭据按租户隔离。

12. 常见问题排查

12.1 "改了代码没生效"

backend 源码 bake 进镜像，需重建：

docker compose up -d --build backend

12.2 缓存不命中

检查：

  1. 是否多轮对话（多轮不走缓存）。
  2. citation_cache_version() 是否变化导致 key 变化。
  3. Redis 是否命中但文档已被治理撤回。
  4. SEMANTIC_CACHE_ENABLE 是否开启。

12.3 检索结果差

排查路径：

  1. /api/retrieval/debug-search 查看每步中间结果。
  2. 检查 routing_decision.route 是否合理。
  3. 检查 RRF 权重、rerank 是否降级、MMR λ。
  4. 检查 ACL 是否误过滤。

12.4 LLM 返回空答案

检查：

  1. LLM_FALLBACK_ON_EMPTY=True 是否生效。
  2. llm_router 熔断状态。
  3. DeepSeek reasoning_effort 是否耗尽预算。

12.5 Milvus 写入失败

常见原因：

  1. MinIO 磁盘水位满 → datanode panic。
  2. etcd 或 milvus-minio 未健康启动。
  3. collection schema 与 embedding 维度不匹配。

12.6 Neo4j 启动失败

可能因断电导致事务日志损坏，已配置：

NEO4J_internal_dbms_tx__log_fail__on__corrupted__log__files=false
NEO4J_db_recovery_fail__on__missing__files=false

如仍失败，可从 MySQL KgTriple 镜像重建：

python scripts/rebuild_kg_from_mysql.py
