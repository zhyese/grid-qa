## 1. H1 检索底座升级 —— ⚠️ 必须先重建向量库

### 改了什么
- `QWEN_EMB_MODEL` 默认 `text-embedding-v3` → **`text-embedding-v4`**（Qwen3-Embedding 系，官方称 MTEB 多语言/中英检索 +15%~40%）。
- `EMB_BATCH_SIZE`（默认 10，v4 官方上限 20，取保守值）、`EMBED_MODEL_GUARD_ENABLE`（默认 true）。
- `qwen_embedding.py`：显式下发 `dimensions=1024`（钉死与既有 collection 对齐）；网关不认该参数时**自动去掉重试一次**。
- **向量空间一致性守卫**：embedding 模型签名（`qwen:text-embedding-v4:1024`）落 Redis `embed:model_sig:*`，启动 + 首次 embed 时比对；换模型/维度未重建 → `degraded(embed_model_drift)` + `/api/system/health/providers` 的 `vectorSpaceStatus=drift`。
- `scripts/rebuild_embeddings.py`：全量重建 + 签名重置 + 验收提示。

### 必须执行的操作（顺序不可颠倒）
```bash
# 1) 确认 .env 已是 QWEN_EMB_MODEL=text-embedding-v4（本次已改）
# 2) 让新模型生效（backend 源码打进镜像，必须重建容器）
docker compose up -d --build backend
# 3) 重建全部向量（旧向量与新 query 不在同一空间，不重建=检索静默变差）
docker exec grid-backend python /app/scripts/rebuild_embeddings.py --yes
# 4) 验收：recall ≥ 92%（不达线则回滚模型名 + 再重建一次）
python scripts/eval_retrieval.py --topk 5 --threshold 0.92
```

### 关于守卫的诚实说明
本次 v3→v4 是**第一次**建立签名基线，Redis 里还没有旧签名，因此守卫**不会**报 drift；它会在首次运行时提示
「向量库已有存量数据但此前无签名基线：若刚更换过 embedding 模型请立即重建」。**守卫的价值在于之后每一次换模型**。
所以第 3 步不能省。

### 回滚
把 `QWEN_EMB_MODEL` 改回 `text-embedding-v3` → 重建容器 → **再跑一次** `rebuild_embeddings.py --yes`。

## 2. H2 切块上下文化

- 入库/向量化时为每个 chunk 用 LLM 生成一句 50~100 字「文档定位语」，**prepend 后再做 embedding**；
  `Chunk.content` 与 Milvus 存储文本**仍是原文**（生成侧与引用原文零影响）。
- 新增列 `chunks.context_line`（`init_db._COLUMN_MIGRATIONS` 幂等补列）。
- 成本护栏：`CONTEXTUAL_CHUNK_MAX_PER_DOC=500`、并发 3、单条超时 20s；单条失败只留空定位语，**不阻塞向量化**。
- 已并入 `citation_cache_version()` 的 `C` 段 —— 开关一变，旧 QA 缓存自动失效。
- 覆盖率查询：`GET /api/system/knowledge/contextual-chunks`。
- 生效方式：开开关 → `scripts/rebuild_embeddings.py --yes`（与 H1 共用同一次重建）。

## 3. F1 数据资产与标注工作台

- 用例资产表 `golden_cases`（category/difficulty/device_tags/expected_sources/label_status）+ 版本表 `golden_set_versions`（sha256 哈希链）。
- `POST /api/golden-set/publish`：校验（口径与 `scripts/validate_golden.py` 完全一致）→ 原子写回 `backend/data/golden_qa.json` → 记版本。**运行时评测链路零改动**。
- CSV/XLSX 批量导入（列名支持中文别名：问题/期望关键词/分类/难度/设备标签/标注状态）。
- `POST /api/golden-set/ingest-quality-events`：把质量事件（dislike/low_faith/eval_low/refused）的坏 case 拉成 `pending` 待标注草稿，按 query 去重。
- `GET /api/golden-set/export/laya`：导出 Laya 三问题原语（choice/noul/score）**冷启动外壳**；gold 标签留空并标 `needsLabel=true`（golden 是检索问答样本，不是告警分诊样本，不伪造标签）。
- 前端：`/golden-set` 页（概览 / 筛选 / 编辑抽屉 / 版本与 diff / 导入 / 发布 / Laya 导出），菜单项按 `golden:read` 显示。

## 4. F2 时序遥测问答

- 新增只读工具 `query_telemetry(deviceId, metric?, hours?, source?)`：查 `ops_telemetry_point`，返回确定性统计（min/max/mean/首末值/变化量）+ 趋势方向（最小二乘斜率）+ 最大单步跳变 + 降采样序列。
- 设备/指标对不上时**不编造**：返回 `availableDevices` / `availableMetrics` 让 Agent 改问；无数据时明确"不得推测数值"。
- 设备名支持模糊匹配；命中多个时要求消歧；租户隔离；仅 `quality=good` 参与统计。
- 前端：Agent 思考链中 `query_telemetry` 步骤旁渲染内联 SVG 迷你趋势图（`TelemetrySpark.vue`），按步骤参数拉只读接口。
- 同时兼容 `PROACTIVE_TELEMETRY_ENABLE`（主动运维侧）——任一开关开启即注册工具。

## 5. F7 Prompt Caching

- `providers/prompt_cache.py`：qwen 显式缓存标记（`cache_control:{type:ephemeral}` 加在最后一条 system 消息，前缀 <1200 字符不标记）；DeepSeek 自动缓存无需标记；方舟/本地只做命中核算。网关不认该参数时**自动去标记重试一次**。
- usage 归一化：`prompt_tokens_details.cached_tokens` / DeepSeek `prompt_cache_hit_tokens` → `usage["cached"]`。
- 计费口径：命中按输入单价 ×10%、创建缓存 ×125%（百炼公开口径，可配）；`savedCost` 落 `cost_track` 日志。
- 成本看板新增「今日缓存命中 Token / 今日节省 / 本月累计」，并显示开关状态。
- 注意：开启 `PROMPT_CACHE_ENABLE` 后 `qa_service` 自动改走 `chat_with_usage` 通道以采集 `cached_tokens`。

## 6. H6 单代理检索循环

- 新增 `deep_retrieval` persona（`max_iter=10`，工具=检索/图谱/案例 + `assess_evidence`），system prompt 内置
  plan→retrieve→grade→refine 循环与**停止准则**（correct 立即停 / ambiguous 最多再 1~2 轮 / incorrect 连续 2 轮必须停并如实说明）。
- 新增只读工具 `assess_evidence(query, topk?)`：复用现成 CRAG（`evidence_strength` + `grade`），不额外调评估 LLM，返回分级、证据强度与「是否应停止检索」的建议。
- 调用：`POST /api/system/agent/run {"persona":"deep_retrieval","query":"..."}`。主链路（非 agent 模式）零改动。
- 观测：`AGENT_CALLS` / `AGENT_ITERS` / `AGENT_TOOL_CALLS`（既有指标）。

## 9. 真实 Docker 栈验证中修掉的 4 个问题（单测测不出来）

单测跑 sqlite + mock，**这 4 个问题只有起真实 MySQL/Milvus 才会暴露**：

1. **F1 建表直接失败**：`golden_cases.query` 原为 `TEXT`，而 `UNIQUE (tenant_id, query)` 在 MySQL 上非法
   —— `(1170) BLOB/TEXT column 'query' used in key specification without a key length`，后端启动即退出。
   修：`query` 改 `VARCHAR(512)` + 应用层长度校验（`MAX_QUERY_LEN`），并加回归测试锁住类型。
   同时 `golden_set_versions.snapshot_json` 改 **MEDIUMTEXT**（TEXT 上限 64KB，数百条用例的快照会被截断）。

2. **Milvus 重启后写路径全挂**：`milvus_client.delete_by_doc / count_by_doc / insert_chunks` 直接
   `Collection(name).xxx()`，**没有 load 集合**。Milvus 重启/compaction 会 release 集合，
   此时 delete/query 报 `collection not loaded` —— 表现为"重建向量、删除文档全部失败"。
   `search` 原本有 not-loaded 重载重试，写路径漏了。
   修：抽出 `_run_with_reload(name, op)`（清缓存 → 重建 Collection 对象 → 重试一次），四条路径统一走它。

3. **重建脚本会清掉不该清的告警**：原实现在**有文档失败时仍调用** `mark_vectors_rebuilt`，
   而部分失败 = **混合向量空间**（部分新模型 / 部分旧模型），比"全部旧"更糟，恰恰最该继续告警。
   修：只有「全量 + 全部成功」才重置签名；`--limit` / `--doc-ids` 视为局部重建，保留告警并打印收口命令；
   部分失败时打印可直接粘贴的 `--doc-ids` 补跑命令。

4. **重建白烧 LLM**：`vectorize_document` 在 `KG_AUTO_EXTRACT_ENABLE` 下无条件后台触发三元组抽取，
   重建 123 篇文档 = 123 次 LLM 抽取，而抽取对同一内容幂等（按 (s,r,o) 去重）→ 结果全被丢弃。
   修：重建脚本内临时关掉本进程的 `KG_AUTO_EXTRACT_ENABLE`（其余入口不受影响）。

**教训**：新增带唯一约束/索引的模型字段时，先确认 MySQL 可索引性；改动 Milvus 读写路径时，
load 状态必须与 search 同等对待。
