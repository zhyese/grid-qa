电网运维 RAG 智能问答系统

机构版原创教材·第一册：课程导论、业务建模与工程基础

本册为重新编写的原创正文，不拼接其他课件。目标不是让学员“看懂几个概念”，而是让学员能够把一个真实运维问题拆解成数据、检索、生成、验证和运营五类工程任务。

本册学习结果

  1. 能向非技术人员解释 RAG 为什么适合运维知识问答。
  2. 能画出从用户提问到答案返回的全链路。
  3. 能在本地启动项目并定位最常见的启动故障。
  4. 能为一类运维场景设计知识字段和黄金问题。
  5. 能用证据、权限和版本三个维度判断答案是否可发布。

第一章 机构课程如何使用

1.1 这不是 API 速成课

许多课程从调用大模型接口开始，学员很快得到一个能聊天的页面，却不知道回答错了以后应该查哪里。本课程把“答案质量”作为主线：先定义业务风险，再设计知识资产，再选择检索策略，最后才讨论模型表达。每个概念都要落到一次可复现的实验。

1.2 五种角色的共同语言

角色关心的问题课堂产出
运维专家答案是否符合规程、是否能执行术语表、风险边界、黄金答案
数据工程师文档如何切分、更新和追溯元数据字典、入库清单
算法工程师如何召回正确证据检索实验报告
后端工程师接口如何稳定、可观测、可降级接口契约、错误码、指标
产品与管理者是否安全、可控、可推广验收标准、权限矩阵

1.3 课堂规则

学员每次提交都必须包含“输入、过程、输出、证据、失败处理”五项。只展示成功截图不算完成；如果实验没有失败样本，说明实验设计还不够真实。

第二章 从一个运维问题开始

2.1 问题拆解示例

原问题：“主变压器油温突然升高，应该先做什么？”这句话至少包含设备对象、异常现象、时间变化和动作请求。系统不能把它当成一段普通文本，而应识别出：设备=主变压器，现象=油温升高，意图=故障处置，输出=步骤化建议，风险=可能涉及停电和人身安全。

2.2 问题的五层模型

  1. 字面层：用户实际输入了哪些词。
  2. 实体层：设备、部件、地点、数值、单位和时间。
  3. 意图层：查询规程、故障诊断、原因解释还是操作建议。
  4. 约束层：用户角色、部门、设备范围和文档生效时间。
  5. 风险层：回答是否可能触发现场操作，是否必须要求人工确认。

2.3 为什么不能只靠提示词

提示词可以要求模型“谨慎”，却不能替代文档版本管理、权限过滤或引用校验。一个真正可用的系统必须在模型之外保存证据、记录过程并允许审计。

课堂实验 1：每组收集 10 条真实或脱敏问题，按上述五层模型标注。要求至少包含 2 条无答案问题、2 条多轮指代问题和 1 条越权问题。提交标注表，并说明每个字段为何影响检索或生成。

第三章 RAG 的工程化定义

3.1 六个阶段

采集：文件、FAQ、工单、设备台账
治理：版本、生效期、责任人、权限、撤回
索引：清洗、分块、向量化、关键词索引
召回：路由、BM25、向量、混合、重排
生成：提示词、上下文、流式输出、引用
验证：格式、相似度、NLI、拒答、审计

3.2 每个阶段的失败方式

阶段常见失败表面现象真正根因
采集扫描 PDF 无文本知识库数量正常但搜不到解析器没有 OCR 或抽取为空
治理旧版本未撤回答案引用过期规程没有生效状态和治理门禁
索引标题与正文被拆开召回片段缺少上下文分块只按字符数
召回型号和数字丢失语义相近但对象错误只使用向量检索
生成模型补全未提供的步骤答案流畅但不可追溯没有证据约束和拒答条件
验证引用编号不存在页面看似有引用只检查格式未检查索引

3.3 可信答案的最低条件

答案必须能回答“依据哪一份文档、哪一个版本、哪一段内容、对谁可见、在什么条件下成立”。如果其中任一项缺失，系统应降低置信度或要求人工确认。

第四章 项目架构与请求生命周期

4.1 分层边界

接入层负责页面和 HTTP；路由层负责参数、鉴权和响应；服务层编排业务；RAG 层实现召回和证据算法；Provider 层屏蔽模型供应商；数据层保存事实；观测层记录指标和追踪。边界的价值在于：更换模型不会迫使页面重写，调整召回不会把权限逻辑复制到每个接口。

4.2 一次流式请求

  1. 前端提交问题、会话和用户身份。
  2. 后端进行安全检查、术语规范化和权限解析。
  3. 系统判断是否为单轮问题，尝试读取缓存。
  4. 未命中时生成独立检索问题并进行路由。
  5. 按策略执行稀疏、稠密或混合召回。
  6. 进行重排、ACL 过滤、MMR 去重和知识治理。
  7. CRAG 判断证据是否足够；必要时改写重检索。
  8. 模型基于证据流式生成，输出引用和完成事件。
  9. 引用校验、指标记录和单轮缓存写入后台完成。

4.3 课堂画图要求

学员必须在图上标出：用户输入、租户和角色在哪里进入；文档版本在哪里过滤；模型调用失败如何降级；引用如何回到 chunk；哪一步产生指标。只画数据库和模型图，不标请求时序，视为未完成。

第五章 环境搭建与第一次运行

5.1 启动前检查

docker --version
docker compose version
Test-Path .env
Get-Content .env.example
docker compose config --quiet

检查的目的不是背命令，而是提前发现端口冲突、配置缺失和 Compose 文件无法展开。模型密钥只放入本地环境文件，不写进讲义、截图和 Git。

5.2 启动与验证

docker compose ps
docker compose logs backend

5.3 三类启动故障

故障第一检查点不要做的事
容器退出查看对应服务日志最后 100 行反复重启而不读日志
页面能开但提问失败后端健康、模型密钥、网络先修改前端提示词
文档上传成功但召回为空解析结果、集合维度、入库状态直接调大 topk
课堂实验 2：每位学员完成启动记录表：时间、命令、服务状态、端口、日志中的一次 warning 及解释。故意停止 Redis 后重新提问，记录系统应如何降级。

第六章 第一轮项目实训

6.1 任务说明

建立“线路跳闸处置知识包”。知识包至少包括 3 份规程、2 份故障案例和 1 份 FAQ。所有材料必须脱敏，并为每份材料填写来源、版本、生效日期、责任部门和可见角色。

6.2 交付步骤

  1. 建立资料登记表并给每份文档编号。
  2. 检查 PDF、Word、表格是否可以抽取文本。
  3. 设计 chunk 元数据，不少于 8 个字段。
  4. 导入系统并抽查 20 个片段。
  5. 编写 20 条问题，其中 5 条要求引用具体规程。
  6. 执行提问并保存答案、引用和检索轨迹。
  7. 挑选 3 个失败案例，写出根因假设。

6.3 验收量表

项目达标优秀
资料登记字段完整率 100%有负责人和撤回流程
片段质量无空文本、可追溯标题、父块、版本齐全
问题集20 条且类型多样含越权、无答案、多轮问题
答案质量有来源和风险提示可解释失败并提出改进

第七章 讲师复盘与课后作业

7.1 讲师复盘问题

  1. 哪些学员把模型能力误认为知识库能力？
  2. 哪些失败其实来自数据，而不是检索算法？
  3. 学员是否能指出权限过滤发生的位置？
  4. 是否有人只看最终答案，没有查看证据？

7.2 课后作业

提交一份不少于 1500 字的《运维知识问答风险分析》，至少讨论：错误答案的后果、过期文档、越权暴露、模型不可用、缓存污染和人工复核。每个风险必须给出预防、检测和恢复措施。
