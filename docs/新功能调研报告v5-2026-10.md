## 一、执行摘要

v4 把视角切到"能不能被采信/审计/运营"（合规、可信、上下文、生态），本轮 v5 回到**系统最老的一层资产——检索底座与 Agent 资产本身**：底座两年没换血、Agent 面扩大后安全没对标、MCP 总线空转。识别出 **6 个全新机会（H1–H6）+ 1 个备选（H7）**。核心判断三条：

1. **检索底座存在代际红利，且是全表确定性最高的机会**。本项目 embedding/rerank 仍是 `text-embedding-v3` + `gte-rerank-v2`（`config.py:102/154`），而 Qwen3-Embedding-8B 已以 70.58 登顶 MTEB Multilingual v2（百炼对应 `text-embedding-v4`，API 兼容可直接切）。升级 = 改两个模型名 + 一次 Milvus 全量重建，`eval_retrieval.py` recall≥92% 门禁现成——**~3 人天换一条全链路质量曲线，性价比无敌**。
2. **2026 生产 RAG 管线共识已把"上下文化切块"纳入标配**：contextual retrieval（切块前注入模型生成的文档定位语）+ 混合检索 + rerank + 引用 + agentic search。本项目结构感知分块（父子/表格/章节）已领先一半，**语义上下文化缺位**——与 H1 共用同一次 Milvus 重建，一次成本双收益。
3. **Agent 资产安全首次有了全球对标框架**：OWASP《Top 10 for Agentic Applications》（ASI01–10，2025-12-09 发布，2026 年落地为 promptfoo 等自动检测）。本项目 `run_agent` 已有 9 个调用方 + 长期记忆 + 外部 MCP 攻击面，而红队底座（52 用例 + `tests/redteam/test_privilege_escalation.py` + `backend/llm_eval_core/` 的 hidden_oracle 场景化 harness）现成——**对标成本极低，产出直接喂 G1 合规报告的"安全可靠性"维度**。

**推荐 TOP3：H1 检索底座代际升级 > H2 切块上下文化 > H3 Agentic 安全对标。**

### H1 检索底座代际升级 —— Qwen3-Embedding（text-embedding-v4）+ rerank 换代

**一句话定位**：把云端 embedding 从 `text-embedding-v3` 切到百炼 `text-embedding-v4`（Qwen3-Embedding，MTEB 多语榜首），rerank 从 `gte-rerank-v2` 评估切换到新一代模型，向量维度保持 1024 不变，一次 Milvus 全量重建。

- **为什么现在**：① Qwen3-Embedding-8B 是当前开源多语第一（70.58），中文电网文本直接受益；② API 兼容（同为 DashScope/OpenAI 兼容 embeddings 接口），代码几乎零改动；③ 本项目 `eval_retrieval.py`（recall<92% 退出码 1）+ `eval_matrix.py` 现成，**升级效果当天可验收**，不符合就回滚模型名。
- **接入点**：
  - `config.py:102` `QWEN_EMB_MODEL: "text-embedding-v3" → "text-embedding-v4"`；`config.py:154` `RERANK_MODEL` 评估换新一代（**以百炼网关实际上架名为准**——DeepSeek 模型名漂移的教训）。
  - `providers/embedding/qwen_embedding.py`（`_BATCH=10` 保持保守；v4 官方单批上限 20，不追上限）。
  - `services/rerank_service.py:39` 已参数化 model，零结构改动。
  - 双 collection（`grid_chunks`/`grid_chunks_bge`）全量重建走既有向量化链路；`citation_cache_version()` 不涉及（answer 语义未变），但 L1/L2 缓存建议随重建清一轮。
- **工作量**：~3 人天（含重建+评测验收+回滚预案） | **优先级**：🔴 **P0（本轮第一）**
- **去重说明**：v4 G 系列无模型代际项；能力收益矩阵只做"开关组合"对照、从未换模型；方向 13 只点名检索范式未涉及底座模型。**全清单无重叠。**

### H2 切块上下文化 —— Contextual Retrieval 工程化（+ Late Chunking/SmartChunk 跟踪）

**一句话定位**：入库时用 LLM 为每个 chunk 生成 50–100 字的"文档定位语"（所属文档/章节/主题），prepend 后再做 embedding（存储原文不变），解决"切块后脱离文档语境、代词/省略主语导致向量失真"——Anthropic 数据：上下文化嵌入降低检索失败率 35%，叠加 rerank 达 49%（厂商自述，需本项目评测复现）。

- **为什么现在**：① 2026 生产管线共识已把 contextual retrieval 列为标配；② 本项目结构感知分块（父子/表格/章节路径/semantic_tags 规则标签）已解决"结构"一半，**"语义上下文"一半缺位**；③ 与 H1 共用同一次 Milvus 重建与全量重嵌入——**合批做，一次成本双收益**。
- **接入点**：
  - `services/document_service` 入库/向量化链路：切块后新增"上下文化"步骤（LLM 批量生成定位语，prompt 入 `rag/prompt_templates.py`），`Chunk.content` 存原文不变、新增 `context_line` 字段（Alembic 迁移）。
  - 复用 `semantic_tags` 的思路与 `embedding_service.embed_texts`（chunk 向量缓存键含 chunk_id，重建时自然绕开旧缓存）。
  - 新增开关 `CONTEXTUAL_CHUNK_ENABLE=False`（默认关=现状），只影响入库链路，问答主链路零改动。
- **工作量**：~4 人天（与 H1 合批另省重建成本） | **优先级**：🔴 **P0（与 H1 同批）**
- **去重说明**：方向 13 只点名 Late Chunking"未做"，从未给出落地路线（v4 对 G6 vs 方向 13 的处理先例：泛提不算覆盖）；v4 G2 是**会话/任务上下文**（预算-压缩-遗忘），H2 是**文档切块上下文**，对象与接入点完全不同。

- **接入点**：

- **去重说明**：**诚实定位——方向 2/F2 已立项"SCADA 真实接入"，v4 也将其归入"已立项不重列"**。H5 的新增量是：① 给出 **MCP 工具化**这一具体协议路径（方向 2 从未定义）；② 修复全仓审计确认的"注册表空转/仅 mock"断点；③ 引用 2026 工业生态证据收敛技术选型。**本质是方向 2 的执行方案升级，非全新方向。**

### H5 视觉文档检索通道 —— ColPali 系 late-interaction（扫描版规程/图纸）

**一句话定位**：为扫描版规程/图纸 PDF 增加"整页视觉向量"检索通道（ColPali/ColQwen 系 late-interaction），检索命中后把页图交 VLM 生成答案——替代"rapidocr 纯文本化丢版面"的现有路径，作为 dense/BM25/KG 之外的第四召回通道。

- **为什么现在**：① ColPali 路线 2026 已生产化（ViDoRe 超 OCR 管线，ColQwen3-omni/Qwen3-VL-Reranker-2B 2026-01 开源，生态配套齐）；② 电网知识库天然有扫描版老规程/图纸（表格/接线图/铭牌照片），OCR 文本化后**空间语义全丢**；③ 效率研究（token budgeting/tile pooling）开始解决多向量成本——但仍是最贵的一项。
- **接入点**：
  - `services/parse_service.py:87`（ocr_pdf）：扫描件分支旁路出"页图 + 视觉向量"产物；`multimodal_service`（`qwen-vl-max`，`VLM_ENABLE=False`）负责命中后的页图理解。
  - 新增视觉 collection（late-interaction 多向量）；**约束**：pymilvus 钉 `<2.5`，多向量能力需先验证（PoC 门禁）；bge 容器资源（cpus:4/mem 10g）需评估加页图向量的内存增量。
  - RRF 融合入口（`rag/rrf.py`）加第四通道；开关 `VISION_RETRIEVAL_ENABLE=False`。
- **工作量**：~8 人天（含 PoC 验证） | **优先级**：🟡 **P2（扫描件存量普查后决定：存量小就不做）**
- **去重说明**：v3 F3（VLM 阅片）是**设备照片→诊断**的生成侧能力；方向 7（多模态）是泛立项。H5 是**文档检索侧**的通道升级，接入点在解析/检索链路，与 F3 正交。

### H6 单代理检索循环 —— Agentic Retrieval（检索即工具 + 迭代预算 + 停止准则）

**一句话定位**：在 diagnose 等 persona 沙箱内试点"检索即工具"的单代理循环：agent 自主决定查什么/查几轮/证据够不够（对齐 2026 生产共识的 plan→retrieve→grade→refine + iteration budget + stop criteria），不碰问答主链路。

- **为什么现在**：① 2026 共识明确：单代理循环是生产主流、多代理编排是高失效率例外——与 v4 判断互证；② 本项目零件齐备：`run_agent` 的 ReAct 循环 + `persona.max_iter`（迭代预算概念已有）+ `search_knowledge` 已是工具 + CRAG grade 可作停止准则信号；③ 主链路 CRAG 的"固定改写重检索"对复杂多跳问题（跨规程/跨设备）覆盖有限，agent 自主多轮是补充解。
- **接入点**：
  - 新增 persona `deep_retrieval`（`services/agent_personas.py`）：工具集 = 检索/KG/案例 + 停止准则入 system prompt；`agent_runtime` 零结构改动（现成引擎）。
  - 停止准则复用 CRAG 的 `evidence_strength`（`rag/crag.py`）作工具返回值的一部分；`SELF_RAG_ENABLE`（休眠）的"是否需检索"判断可并入试点对照。
  - 观测走 `qa_trace_service` + `AGENT_ITERS` 指标（已注册）。
- **工作量**：~5 人天（含与主链路 CRAG 的对照评测） | **优先级**：🟡 **P2**
- **去重说明**：v4 不追的是**多 Agent 编排扩展**；CRAG 自纠错是**管线内固定流程**（改写→重检索→拒答，非模型自主决策）；H6 是**单代理自主检索决策**，且只在 persona 沙箱内、主链路零改动。

### H7（备选）电网智能评审辅助

国网信通 2026 半年报披露"基于光明大模型的**电网智能评审**技术落地"。本项目 `doc_signoff_service` 批注签批链路（哈希留痕）是邻接底座，可做"LLM 预审意见 + 人工签批"增强。**证据仅一句新闻、无技术细节，仅备选观察，不入主路线**。

## 五、优先级总表与路线建议

| 排名 | 功能 | 价值 | 工作量 | 关键依赖 | 建议 |
|---|---|---|---|---|---|
| 1 | **H1 检索底座代际升级** | ★★★★★ | ~3 天 | 无（API 兼容） | **立即启动**——全表确定性最高，eval 门禁当天验收 |

| 3 | **H3 Agentic 安全对标** | ★★★★ | ~5 天 | 无（红队底座现成） | 并入 v4 合规三件套作"第四件" |

| 5 | **H6 单代理检索循环** | ★★★ | ~5 天 | 无 | persona 沙箱试点，对照 CRAG 评测 |
| 6 | **H5 视觉文档检索** | ★★★ | ~8 天 | pymilvus 多向量 PoC + 扫描件存量 | 存量普查后决定 |

**路线建议**：
1. **检索底座批（H1+H2，~7 人天）单独成批**：两者都动 Milvus 全量重建，合批做省一次重建；验收统一走 `eval_retrieval`（recall≥92%）+ `eval_matrix` + golden 对照，不达线即回滚（模型名/开关双回滚点）。与工作区在飞的"默认开新常态"改动**错峰落库**，避免两轮基线混淆。
2. **H3 并入 v4 合规三件套**：G1+G3+G7+H3 构成"评测合规 + 治理闭环 + 审计追溯 + 安全对抗"完整叙事，H3 的红队数据直接作 G1"安全可靠性"维度证据。
3. **H4 数据门禁制**：Stage 0（asyncua 模拟源，2 人天）随时可做；真实 OT 数据拿不到就停在 Stage 0，不硬上。
4. **H6/H5 观察位**：H6 等 H1/H2 落地后新基线上再试点；H5 先做扫描件存量普查（一行 SQL 的事）再立项。

**与 v4 G 系列 / v3 F 系列的关系**：H 与 G/F 无重复且互补——G 系列是"治理/合规/上下文"（对外可信），H1/H2 是"检索底座换血"（对内提质），H3/H4 是"Agent 资产安全与实工具化"（G 系列未触碰的两块）；F3 与 H5 分列生成侧/检索侧，F5/G4 与 H4 分列协议层/数据层。
