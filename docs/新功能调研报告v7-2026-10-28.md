## 一、执行摘要

v6 的收口批**绝大部分已落地并开闸**（.env 里 GOLDEN_SET / OPS_WORKBENCH / TELEMETRY_QA / PROMPT_CACHE / AGENTIC_RETRIEVAL / CONTEXTUAL_CHUNK / CRAG_V3 / CRAG_PERDOC 全部 =true；P0-2/3、P1-5/6/7/8/9/11 均有对应提交）。仅 **P0-4（H1 向量重建与检索验收）** 与 **P1-12（Nacos 决策）** 两项仍欠，属欠账不属新功能，本轮只作提醒。

v7 的增量判断三条：

1. **P0 不是新功能，是五个隔离/配额缺口**。强监管行业里这是红线级问题，且修复成本极低（A1/A3/A4 各 0.5 天，A2/A5 各 1 天，合计 ~3.5 天）。**先修再建**——新功能建在漏水的桶上，做得越多亏得越多。其中 **A5 尤其要紧**：它是 v6 收口批新开的文档资产端点带来的，属于"上一轮收口带出来的新洞"。

3. **真正的空白在"问之外"**：设备健康画像、多模态现场作业、对外 OpenAPI/MCP 生态、租户自助——这四块是行业 2026 的落地重心，本项目零件齐备但入口为零。

**推荐 TOP3：P0 隔离修复 > N1 处置回填闭环 > N2 设备健康画像。**

## 三、本轮审计发现：建成了但漏水（v6 视角盲区）

> 以下五条均为**代码实读确认**，非推测。修复成本低、风险收益比高，建议作为 v7 的 P0 批次。

### A1 · hotqa 高频问答跨租户泄漏 🔴

- **事实**：写侧 `feedback_optimizer_service.py:378` 用 `key = f"hotqa:{nq}"`，租户只写进 payload；读侧 `qa_service.py:135` 同样用 `f"hotqa:{nq}"` 取，**全程不与当前 tenant 比对**。
- **签名佐证**：`_hit_hotqa(nq, conversation_id, t0)`（`qa_service.py:121`）**连 tenant 形参都没有**——调用点 `qa_service.py:766` / `:1402` 也不传。而同级的三级缓存 `_cache_key(model_type, query, tenant)`（`:96`）、语义缓存 `semantic_cache_get(..., tenant_id=tenant)`（`:826`）都带租户。
- **测试佐证**：`tests/test_hotqa_hit.py` 共 8 个用例，**无一覆盖租户隔离**；而 `tests/test_cache_tenant_isolation.py` 已锁住 L1/L2 key 与语义缓存索引的租户隔离——**hotqa 是这套契约里唯一没被覆盖的缓存层**。
- **后果**：租户 A 的用户点赞某答案 → 租户 B 提同样问题 → 直接返回 A 的答案与 A 的文档来源。`hotqa` 优先级最高（`qa_service.py:760`，跳检索/CRAG/生成），**且不受三级缓存版本串约束**。
- **修法**：`_hit_hotqa` 增加 `tenant` 形参；key 改 `hotqa:{tenant}:{nq}`；读侧校验 `payload.tenant == tenant`；旧 key 做一次性兼容读或直接废弃（无 TTL，需清理）。同步在 `tests/test_cache_tenant_isolation.py` 补一条 hotqa 用例。工作量 **0.5 天**。

### A2 · 复杂问题分解绕过租户与 ACL 🔴

- **事实**：`query_plan_service.py:70` `mixed_search(db, query_text, topk, model_type=model_type)` —— **不传 tenant、不传 user_dept/user_role**；`routers/domain.py:286` 调 `plan_and_answer(db, body.question, body.modelType)` 也不传用户上下文。
- **后果**：`/api/domain/query-plan` 的检索跨全部租户、且绕过文档级 ACL。对比 `retrieval_service.py:504-522` 的过滤条件——不传这几个参数时整段过滤被跳过。
- **同类**：`mcp/server.py:201` `mixed_search(db, query, topk)` 同样无租户（MCP server 对外暴露 6 个工具）；`debate_agent_service.py:121` 同样无租户。
- **修法**：`plan_and_answer` 增加 `tenant/user_dept/user_role` 形参并透传；MCP server 从 `X-Tenant-Id` 头取租户（`realtime_event.py:47` 已有先例）。工作量 **1 天**。

### A3 · 反馈统计跨租户（注释过时导致） 🟠

- **事实**：`models/feedback.py:26` **已有** `tenant_id` 列；但 `feedback_fix_rate_service.py:31` 与 `doc_quality_service.py:55` 的注释仍写"Feedback 表当前无 tenant 列"，代码据此做全表扫描（`feedback_fix_rate_service.py:37-41`、`doc_quality_service.py:69-75`）。
- **后果**：修复率、文档质量 issue 的分子分母混入他租户数据——指标失真，且 `doc_quality` 会因他租户的差评给本租户文档打标。
- **修法**：两处补 `Feedback.tenant_id == tenant` 过滤 + 改注释。工作量 **0.5 天**。

### A4 · 配额只展示不强制 🟡

- **事实**：`cost_tracker_service.py:126 check_quota()` 全仓唯一调用点是 `routers/system.py:876`（`GET /cost/quota` 查询接口）；`qa_service.answer/stream_answer` 入口**无配额校验**。
- **后果**：`_DEFAULT_QUOTA` 是摆设，超配额后照常调用 LLM。
- **修法**：`qa_service` 入口加一次 Redis 读（已有 `cost:user:*:monthly` 计数，零新增存储），超限返回结构化拒答。工作量 **0.5 天**。注意别做成同步阻塞——复用现有 `degraded` 降级语义，检查异常放行。

### A5 · 文档资产接口按 doc_id 直达，无租户校验 🟠

- **事实**：v6 收口批新开的文档资产端点只挂了 `require_perm`，**没有租户归属校验**——
  - `routers/document.py:86` `get_stats(db)` 不传 tenant（`document_service.py:457-461` 全表 `group_by`）→ 看板统计跨租户；
  - `routers/document.py:110` `list_versions(db, doc_id)`、`:122` `rollback_version`、`:222` `list_chunks`、`:230` `update_chunk`、`:240` `find_similar_docs`、`:249` `diff_versions` —— 全部只收 `doc_id`，服务层 `get_document`（`document_service.py:171-175`）只按 id 查、不校验 `tenant_id`。
- **后果**：知道 doc_id 即可跨租户读版本、读分块、甚至改分块并触发重向量化（`update_chunk` 需 `doc:manage`，但跨租户 editor 同样满足）。`_assert_acl`（`document_service.py:47-58`）只查 dept/role，**不查租户**。
- **对照**：`list_documents`（`document_service.py:140-141`）是**正确示范**——`where(Document.tenant_id == tenant_id)`。
- **修法**：`get_document` 增加可选 `tenant_id` 形参并默认校验（内部调用方传当前租户）；六个资产端点路由层补 `user.tenant_id` 透传。工作量 **1 天**。这条与 A2 同属"v6 新开入口漏了隔离"，建议同一批修。

## 四、新功能候选（N 系列）

> 每条标注：定位 / 为什么现在（一手证据）/ 接入点 / 工作量 / 优先级 / 去重说明。

### N1 · 处置回填闭环 —— 打通数据飞轮最后一环 🔴 P0

**定位**：操作票执行完成 → 自动生成"处置经验"草稿 → 人工审核 → 回流知识库 → 下次同类故障可检索。这是 v1 报告画过、至今没接的一条线。

- **为什么现在（证据）**：`ticket_lifecycle_service.py:327 _emit_ticket_event` 已 emit `ticket.issued` / `ticket.completed`（payload 含 steps/executionLog/deviation），但全仓**质量事件总线** `subscribe(...)` 只有 3 个业务订阅点——`feedback.dislike`（`evidence_gap_service.py:426`）、`governance.doc_blocked`（`governance_propagate_service.py:245`）、`retrieval_eval.eval_low` + `online_eval.low_faith`（`retrieval_tune_service.py:156-157`）。**`ticket.*` 零订阅者**。
  - 注：另有 Bus A 域事件 `register_event_handler` 5 处（`llm_user_integration_service.py:106/113`、`realtime_event_service.py:185`），那是 `DomainEvent` Outbox 总线，与 `quality_event_bus` 是**两套不同总线**——`ticket.*` 走的是后者，确认无订阅。
- **接入点**：新增 `services/ticket_reflow_service.py`，`subscribe("ticket.completed", handler)`；handler 复用 `knowledge_evolution_service` 的草稿表与审核流（已有 `KnowledgeEvolutionDraft` + review/withdraw/reflow 端点），把 `task + steps + executionLog + deviation` 拼成草稿，`source="ticket_reflow"`；审核通过走既有 `reflow` 回流入库。注册时机沿用 `evidence_gap_service.py:423` 的"import 时注册一次 + 幂等"写法。
- **护栏**：默认开关 `TICKET_REFLOW_ENABLE=False`（关=现状）；草稿必须人工审核才入库，绝不自动进主库（沿用"AI 自进化内容降权或可撤回"的既有边界）。
- **工作量**：~2 天 | **优先级**：🔴 P0（纯接线，零新架构）
- **去重**：v6 的 G3 是"答案级自检+归因+复核台"（问答侧质量治理），N1 是"处置侧经验回流"（工单侧），对象与事件源不同。

### N2 · 设备健康画像与检修建议 🔴 P1

**定位**：以设备为主键，聚合遥测趋势 + 历史工单 + 图谱故障链 + 文档质量，输出一页"设备体检报告"与检修建议。运维人员的主入口从"提问"变成"看设备"。

- **为什么现在（证据）**：零件全齐但没串起来——`telemetry_history_service.series`（F2 已开闸）、`device_dossier_service.dossier`（`routers/ops_workbench.py:133` 已暴露，回事件/运行/票据时间线）、`kg_service.graph_context`（故障链）、`fault_prediction_service.predict`（纯统计 riskScore，自注释"无模型"）、`ticket_lifecycle_service`（历史工单）。前端 `OpsWorkbench.vue:108` 已有 5 个 Tab（规程变更/交接班/设备档案/遥测历史/表格查询），**设备档案与遥测历史是两个互不相通的 Tab**——健康画像就是把它们并到一页。
- **接入点**：`services/device_health_service.py` 聚合四源 → 新增 `GET /api/ops-workbench/devices/{id}/health`（`require_perm(OPS_READ)`）；前端在 `OpsWorkbench.vue` 的 tabs 数组加一项"设备健康"，复用 `TelemetrySpark.vue` 画趋势。
- **硬约束（必须先对齐）**：`device_dossier_service.dossier` 第 29-30 行要求设备存在 `RealtimeDeviceMapping.canonical_device_id` 映射，否则 404"设备未建立有效规范ID映射"。**没有映射的设备做不出健康画像**——落地前要么先补映射（`PUT /realtime/device-mappings` 已存在），要么在 UI 上明确提示。这是本条最大的落地风险，不要低估。
- **不做**：不训练模型。`fault_prediction_service` 的教训（自注释"纯统计+规则"）说明数据没进来前上模型是伪需求；先把四源聚合做扎实。
- **工作量**：~4 天（含映射缺失的 UI 兜底）| **优先级**：🔴 P1
- **去重**：v6 的 H4 是"真实遥测接入"（数据源侧），N2 是"数据已进来之后怎么用"（应用侧）。方向 6（时序问答）是问答入口，N2 是设备入口。

### N3 · 多模态现场作业通道（VLM 开闸 + 入口） 🟠 P1

**定位**：现场照片/红外图/表计屏显/检修前后对比 → 结构化识别 → 接入问答与诊断。解决"扫描件 OCR 后空间语义全丢"和"现场人员只能打字描述"两个痛点。

- **为什么现在（证据）**：`multimodal_service.py` 已有 6 个函数——`describe_image`(125)、`analyze_infrared`(146)、`analyze_meter_reading`(171)、`compare_images`(193)、`needs_image_search`(235)、`describe_image_for_retrieval`(242)。**全仓唯一调用方是 `document_service.py:268` 的 `describe_image`**——另外 5 个是零调用方的死能力。`VLM_ENABLE` 默认 False 且 .env 未配置。文档上传已允许图片（`document_service.py:21` 注释"含扫描件/图片"）。
- **接入点**：新增 `routers/vision.py`（`POST /api/vision/infrared`、`/meter`、`/compare`、`/describe`，`require_perm(DOMAIN_USE)` + `@limiter.limit`）；前端 Chat 输入区加图片上传（`Chat.vue` 当前只有文字输入 + 语音按钮，无附件能力），识别结果作为一条 context 注入 `build_messages_with_history`。`needs_image_search` 可用于路由：命中图片意图才走 VLM，避免无谓调用。
- **护栏**：开关默认 False（=现状）；`_call_vlm`（`multimodal_service.py:108-122`）已有 try/except + `degraded`；单图 max_tokens 500-600 已设上限。
- **工作量**：~3 天（含开关与前端上传） | **优先级**：🟠 P1（性价比之王，v6 已判 F3 为"开闸+对照评测几乎零开发"）
- **去重**：v5 的 H5（ColPali 视觉文档检索）是**检索侧**第四通道；N3 是**生成侧**现场图片理解，接入点完全不同。

### N4 · 问答 → 操作票一键起草（真闭环） 🟠 P1

**定位**：Chat 里看到处置方案，一键生成带步骤/安措/风险的操作票草稿并进入审批流，而不是跳到工单页重新填。

- **为什么现在（证据）**：`Chat.vue:272 actToTicket(m)` 只是 `router.push({path:'/ticket', query:{task: m.query.slice(0,60)}})`——**只带 60 字问题，不带答案、不带引用、不带证据**。而后端 `agent_tools._t_create_ticket`(51) 与 `domain_service.generate_ticket`(166) 都已能生成结构化草稿。
- **接入点**：新增 `POST /api/domain/ticket/from-answer`（入参：query/answer/sources/conversationId），服务层调 `generate_ticket` + `create_ticket`（`source_ref` 用 traceId 做幂等，`models/ticket.py:28` 已有唯一约束）；前端 Chat 答案操作条加"📋 生成操作票"按钮，生成后跳转带 `ticketId`。
- **护栏**：只生成**草稿**，审批流不变；`TICKET_ACTION_LOOP_ENABLE` 门控；写操作走 `require_perm` + 审计。
- **工作量**：~2 天 | **优先级**：🟠 P1
- **去重**：方向 1（问答→行动闭环）已落地了"告警→建议→转票"这条（`realtime_event_service`），N4 补的是**问答侧入口**——`Chat.vue` 至今没有真正的建票能力。

### N5 · 租户自助与配额治理 🟡 P2

**定位**：租户创建/停用/配额配置/用量看板，从"注册时手填 tenantId"变成可运营的多租户。

- **为什么现在（证据）**：`schemas/auth.py:14 tenantId` 只是注册时一个字段；`routers/system.py` 无任何 tenant CRUD；`cost_tracker_service._DEFAULT_QUOTA` 是硬编码常量（`cost_tracker_service.py:25`）。配合 A4 的配额强制，才有意义。
- **接入点**：`models/tenant.py` + `services/tenant_service.py` + `/api/system/tenants`（`require_admin`）；配额从常量挪到租户记录；`cost_tracker` 读租户配额。
